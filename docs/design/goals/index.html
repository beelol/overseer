Goals

A goal is a condition in plain words and how it is checked: a command that must pass, Overseer reading the work, or you saying so. An agent keeps going until its goal holds; Overseer can have one too. Static mockups for the design in docs/rfcs/orchestrator.md (Goals). Nothing here is built.

An agent with a goal

The agent's row carries one goal line under its title. In its chat the goal is pinned above the composer; each check is a thin line between turns, and each continuation reads as a turn from Overseer that says why it is not done yet.

Overseer's own goal

Set by talking. Overseer reads the goal and its check back and waits for a yes, at every level. Then the goal is pinned at the top of the conversation with who set it and when, and Overseer reports only when it holds, is stuck, or needs you.

Done, stuck and waiting on you

The three states that reach you. Each says why in one sentence and carries its evidence; none shows an internal id or an error code. Done and stuck also notify you when you are away.

While an agent's goal waits for a recovery (a usage limit, say), its line reads paused: continuing on your other account; it keeps its count and goes on after the new account's first turn.

Choices for you

1An agent goal's default limits

  1. 20 tries or 4 hoursproposed
  2. 10 tries or 2 hours: cheaper, stops sooner
  3. No default: you give a limit with every goal

2Setting Overseer's goal at Auto

  1. Always a yes, as aboveproposed
  2. At Auto it goes after the 2-second window, like other things you type

3Claude Code agents

  1. Use Claude Code's own /goal, with Overseer's check when it stopsproposed: fewer restarts, but Claude decides when to stop
  2. Overseer continues every agent the same way: one behaviour and one count across Claude Code and Codex
