# Browser and permission integration assessment

Owner request, 2026-10-03: consistent browser use and all harness capabilities accessible through pending requests, using Overseer's permission interface wherever the native protocol permits. AC-274 records the requirement. This is source inspection, not runtime qualification.

At main9dc165d0, daemon/src/adapters.rs normalizes Claude `can_use_tool` requests into Permissions and returns `allow`/`deny` control responses. Other Claude control-request subtypes remain Unparsed. Codex app-server command/file/permission requests are normalized, but its generic answer serializes `{decision: ...}` for all requests. The documented `item/permissions/requestApproval` instead expects granted permissions and turn/session scope. `mcpServer/elicitation/request` and user-input requests fall through to the unsupported-request error. These existing bridges do not establish complete capability support.

The [official Codex app-server contract](https://learn.chatgpt.com/docs/app-server) documents delegated command/file approvals, scoped permission grants, and MCP form/URL elicitations. An Overseer UI can collect and forward those answers using the native schemas; it does not replace their enforcement. The [official Claude Chrome documentation](https://code.claude.com/docs/en/chrome) describes site permissions inherited from the Chrome extension and connection-mode-dependent prompting. Do not infer that a generic tool allow also grants extension site access. Installed-version and stream-transport qualification remain necessary.
