## Existing contract and authority

The approved Task6 plan and owner answer at the end of `docs/rfcs/mods.md` permit Look reads, Steer changes to installed text bindings, and owner-confirmed preview/install/update/removal. Owner-only locks remain beyond Gate S. Older RFC paragraphs saying “never installs” precede that owner answer; they are not a new planning approval requirement. External programs, transformer adapters and source discovery/generation are outside this bounded text-management slice.

`overseer/mod.rs` already routes native `propose` and `answer` through the shared proposal path. The accepted publication fix takes the turn-start guard **before** resolving the token, captures a typed `NativeOrigin` (caller run, session, exact recorded turn and cause), then releases the guard before action checks/effects. Session insertion revalidates current session/run and recorded turn/cause under the Store lock. New Mods actions must remain inside `propose`, inheriting this path; do not add a native mutation tool or fall back to latest owner authority. Reads must not create an Overseer session. Existing legitimate pending global question answers remain unchanged; this work adds no question-session ownership rule.

`overseer_answer` atomically claims an open/settling proposal as answering before effects, so Voice/Talk/VS Code/TUI/phone answers share one operation. Reuse it, including ordinary No doing nothing. Source text, agent findings and web content cannot supply owner confirmation. Confirm operations require the existing recorded owner/voice cause even at Auto; check-in/needs exceptions apply only to their existing actions.

## Concrete readiness gaps

1. **Classification is currently by action name.** `ACTION_CLASSES`, `QUIET`, final `confirm`, and voice immediate handling all need operation-aware classification for `mod`; model-supplied `class`, `confirm`, actor or role fields cannot select authority. Bind/unbind are Steer; preview/install/update/remove are Confirm; creating/changing/removing an owner lock is Never. Do not add the whole `mod` name to QUIET: self-started nonquiet Steer keeps the current open-card behavior, while Auto and owner/voice settling keep existing policy. Unknown operations refuse.
2. **Generic agent validation is unsuitable.** Except special cases, proposals require `agent` and reject the Overseer run and native children. A strict Mods branch must run before those generic checks, use `ModScope` with canonical repository/run IDs, and permit the separate Overseer scope. Do not weaken other actions' self-action/native-child/Swarm restrictions. A binding affects future qualified turns only, never grants new roles/tools or resumes paused work.
3. **Current mutators are local-owner helpers.** `bindings::set/unset` only test `server::actor()` (remote-device restriction), label writes as owner/user, and allow the owner to edit/delete an existing locked binding. They do not authenticate a Gate S origin. Reusing them unmodified would misattribute changes and omit the required lock policy; clearing the actor is not a solution. Extract shared validation/transaction code with an explicit, internal governed caller policy; retain every existing public RPC/gateway guard. Check lock status, revision, version pin and conflicts under the mutation's Store lock. Deny `locked:true`, any lock-field change, any edit/unbind of an existing locked binding, and narrower overrides/conflicting styles already blocked by the resolver. Record the actual proposal/source attribution, without changing selector roles into permission roles.
4. **Removal also changes bindings.** `library::remove` deletes every matching binding without a locked check. Governed removal must refuse a version referenced by a locked binding, even if the owner confirms the Gate S card; manual owner unlock remains available on management surfaces. Check this in the same transaction as deletion, not only when proposing.
5. **Installation has no revision precondition.** `remove` and binding mutations already enforce `expected_revision`; `install` currently has immutable preview bytes and replay protection but no expected revision. Add a governed precondition inside the existing install transaction. Match preview ID, fingerprint, operation and reviewed library revision; update still uses `mods.install`, not nonexistent `mods.update`. Preserve existing local APIs and install replay behavior. Installation never enables; update never migrates pinned bindings.
6. **Private command identity needs protection.** Session proposals recursively redact their checked actions before storage. That is appropriate for public cards but can alter exact repository/filter/source strings later used for execution. A synthetic credential-shaped exact-filter/path test should establish this boundary before implementation. Keep immutable execution parameters private and public projections redacted, e.g. a small proposal-linked private Mods command record stored atomically with proposal insertion; do not broaden the redaction change to unrelated actions. Public cards expose reviewed operation, readable target, version/fingerprint/revision, consequences and redaction notice. Exact raw parameters never come back from a card answer.
7. **Failure state must be truthful.** Generic `perform` errors currently become a “Done: … failed” result. A stale/locked/removed-preview Mods outcome must report not applied and leave the library unchanged. Handle the specific new outcome without changing all existing proposal behavior. For an initially bounded implementation, one Mods operation per proposal avoids promising atomic batches across heterogeneous actions; this is a proposed implementation limit for root review.

## Bounded delivery order and files

**Read slice:** add `mods` read tool with `list` and `why` only, strict arguments, public decoded-value redaction and the incumbent bounded tool response. No full mod text/source contents required. Recommended permission boundary: Overseer may list/inspect any target; watcher capability (including an ordinary agent assigned as watcher) may inspect only its actual current subject, with a filtered relevant-library summary; ordinary agent may inspect only itself. This exact read projection is a recommendation for root review, not a broader permission grant. A dedicated operation-aware guard is needed because `why` currently accepts `run_id`, while the existing watcher `SUBJECT_READS` guard expects `id`; simply adding `mods` to that name array is insufficient. Reads must not preview, install, bind, execute, create a session or query model servers.

**Installed-text Steer slice:** strict `mod` action parser and daemon classification; shared guarded bind/unbind transactions; concise descriptions/guidance for both tool-capable and text-fallback Gate S. Preserve all five scopes, exact filters and pins, narrower on/off semantics, locked style precedence and separate Overseer binding. Reuse existing level/cause/settling/answer machinery.

**Confirmed library slice:** governed text preview/install/update/remove and explicit reviewed identity; safe public cards, stale checks and once-only execution. The plan classes preview as Confirm, so a preview request itself waits for owner yes before filesystem staging. Its completion produces a preview, not an installation; install/update gets a separate reviewed Confirm card referencing that staged snapshot. This avoids treating confirmation of “show a preview” as permission to install unseen bytes. No arbitrary source download, code build/execute, programs/hooks/tools/limits/harness-option activation, or Less tool noise installation.

Expected ownership expands the plan's original file list: `daemon/src/overseer/{mod.rs,control.rs,session.rs}`, narrowly shared `daemon/src/mods/{bindings.rs,library.rs}` and possibly `daemon/src/store.rs` for private command storage; new `daemon/tests/mods_gate_s.rs`. Existing owner RPC tests must run because shared mutators change. No VS Code/phone/TUI shell redesign or separate voice installer.
