# AC274 Harness Capability Inventory and Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement each bounded task only after the coordinator assigns a builder slot. This is a reviewed design; implementation follows the owner-authorized goal and coordinator assignments. It is not native qualification. All new interfaces below are proposals, explicitly distinct from current APIs.

**Goal:** Route each delegated approval, structured question, and external authorization through one shared, correctly typed pending-request lifecycle without changing harness/provider/OS enforcement.

**Architecture:** Preserve native request identity and raw envelopes in daemon-private storage, expose a redacted discriminated request to every surface, and serialize a native reply selected by its method/version. Machine RPCs remain machine operations. External browser/provider authority gets an observable authorization step rather than a fake Allow result.

**Tech Stack:** Existing Rust daemon/shim/SQLite, protocol/protocol.json and existing generator, VS Code JavaScript, Rust TUI, shared TypeScript phone model and React Native screens. No new browser implementation is presumed.

**Spec:** Main `324e7c8c`, `docs/overseer-rfc.md:664` AC274; `docs/audits/2026-10-03-browser-permissions.md`; AGENTS.md and `docs/goals/handoff.md`. Source inspected in the PR52 worktree; the criterion addition is docs-only and implementation remains separate. PR56 is frozen clean at a6eba48e.

## Global constraints

- AC274 remains unchecked until the complete installed-version inventory, native/mock-provider captures, isolated browser flows, and all listed lifecycle/surface cases pass. Fixture-only or unavailable routes remain gaps.
- No paid Claude turn. Any later paid Overseer qualification uses only gpt-5.6-luna, low effort, one attempt per condition. No retry loops.
- Never use, modify, inspect credentials from, restart, or deploy to the owner's daemon/browser profiles. Dev browser profiles and dev daemons are isolated; native Chrome authentication remains a separate qualification constraint.
- No build, Rust test, UI launch, provider request, login, profile/config mutation, or repository edit occurred in this audit. Local `--help`, `--version`, schema generation into /private/tmp, binary source inspection, and official web reads are the evidence.
- Native persistent grant choices must show the actual target and destination and be explicitly selected. An Always label is display text, never authorization identity. Do not bypass classification/phone scope/voice approval provenance.

## Review focus

1. Two simultaneous requests in one agent must not overwrite or conflate each other, including same itemId with different native approvalId (Task2).
2. A session offer for command A must not silently authorize command B, a different host/port, agent, thread, or generation (Tasks1/2).
3. Stale, revoked, expired, or disconnected replies must not produce a second native response; ambiguous stdin delivery stays visible and is not blindly retried (Task2).
4. Secret form fields, token-refresh payloads, URL query credentials, and raw tool inputs must not enter public events, phone outbox, logs, or watch-device state (Tasks1/2/3).
5. Opening external authorization is not completion; loss of its connection or lack of an authoritative outcome must leave an honest pending/unknown state (Task4).

### Machine requests are not owner prompts

The other four installed Codex ServerRequest families are item/tool/call, account/chatgptAuthTokens/refresh, attestation/generate, currentTime/read. Dynamic tool calls execute host-advertised tools and return DynamicToolCallResponse; never let a raw tool name acquire host capabilities. Token refresh belongs to an authenticated token provider, not a token-entry form; do not expose its response to pending UI. Attestation requires the actual host identity implementation, never fabricated attestation or owner click. currentTime/read is a deterministic host service with its schema response. If not configured/qualified, return the native unsupported error and record a redacted diagnostic explaining unavailable host capability; do not create four human approval cards. Tool execution can independently trigger a real typed pending approval where its host policy delegates one.

Claude hook_callback is similarly a host callback for configured hook IDs, not permission consent. Existing launch does not register SDK callbacks; never acknowledge an unknown callback as if executed. Host→CLI initialize/control requests and MCP message transports are machine plumbing, not independent owner authorization. Official [SDK source](https://raw.githubusercontent.com/anthropics/claude-agent-sdk-python/main/src/claude_agent_sdk/_internal/query.py) is a useful primary cross-check but currently lacks the newer elicitation/user-dialog handlers present in this installed binary; do not substitute its coverage for2.1.288.

## Browser availability and authority

[Official Browser documentation](https://learn.chatgpt.com/docs/browser) says the built-in browser is unavailable in Codex CLI/IDE; desktop computer use is a different route. The presence of CUA in this audit's Codex desktop host does not make it a tool in an Overseer-launched CLI. Installed app-server schema has no browser request family. A specifically configured browser MCP can be a viable Codex route, subject to its own connection/tool schemas and permission policies; no such configuration, browser server, extension or account was inspected/qualified here. Web search/fetch is not navigation/interaction/screenshots.

Claude help/native code exposes Chrome tooling; that establishes a candidate native route. [Official Chrome documentation](https://code.claude.com/docs/en/chrome) describes Chromium-extension and account prerequisites, separate site controls, and mode/connection-dependent prompting. Navigation/DOM interaction/screenshots can use the native Chrome tool family when connected, but the installed stream-json handshake and delegated versus extension-retained approvals need captures. Do not assume generic tool Allow changes extension site permission. No extension installation, connected browser, authenticated profile, selection dialog, site approval or tab isolation was inspected. OS screen capture/accessibility and provider login remain external authorities. This audit makes no native browser usability claim.

External capability status must distinguish available+qualified, available+unqualified, unavailable, and externally blocked, with version/transport/evidence. Disabled/absent integration is an actionable status, not a spinning permission. Runtime qualification must include Chrome's session/tab-group boundary and an isolated MCP-browser context per agent; concurrent agents must not share grants or tabs. Site+port/scheme/redirect/new-tab targets and sensitive operations are independent of a general network.enabled grant.

## Evidence-backed code gaps and bounded priorities

1. **Schema-correct encoding first:** adapters.rs:531 generic reply uses one Codex decision; parse_codex_app:750 aliases native methods; parse_claude:976 admits only can_use_tool. Normalization drops exact family/subagent/browser metadata. Correct known family responses before browser expansion.
2. **Multiple pending and exact identity:** daemon.rs:2942 writes one runs.attention via store.rs:1702; a second pending request replaces the first. claim_run_attention:1709 arbitrates only this one bool request. Use a collection keyed by run+process generation+native request ID/type+thread, not a single slot. Same raw JSON-RPC id reused by a restarted harness cannot refer to an old request.
3. **Grant authority candidate:** Codex command Always offer is constant `this command for the rest of the session` (adapters.rs:767); daemon.rs:2954 checks store.allowed_for_session(run,label):1727 and auto-answers later matching labels. Therefore different command/native context can be matched by label. Source proves the unsafe matching mechanism; a deterministic changed-command mock regression is required before calling the live runtime affected. Preserve this as a concrete candidate, not a paid/runtime result. Prefer native caches; if host replay is necessary, require exact native request-family/offered grant identity and enforce scope/lifetime. No generalized same-label authorization.
4. **Resolution and dispatch:** answer_permission_with:2485 claims before send, unclaims on send error and sets running after shim write. send_stdin:2366/shim.rs:433 acknowledges write/flush, not protected-operation completion. Partial write/timeout can be ambiguous: never blindly unclaim/retry and manufacture two replies. Need generation-bound claim/dispatch receipt, visible uncertain state and native resolved/item outcome handling. No generic RPC offers grant revocation in installed schema (permissionProfile/list only); qualify native session shutdown/replacement or actual documented revocation mechanisms rather than inventing a revoke API.
5. **Redaction separation:** events recursively redact (daemon.rs:3939), but current attention stores raw input before public event redaction. New raw envelopes stay private; public state uses a sanitized projection with opaque choice IDs. Scope values and native IDs used for encoding come from the private original, never from redacted UI text. Secret user answers remain memory-only through send, excluded from event/history/replay/outbox; token/attestation responses never reach clients.
6. **Shared rendering/protocol:** protocol Attention:39 and run.permission:820 represent a string request ID plus bool; schema even omits existing Always optional input. extension run-actions.js:68, on-screen.js, conversation renderer; TUI app.rs:1869; phone/model conversation.ts:829/1387 and phone/src/screens/conversation/rows/PermissionCard.tsx/answers.ts expose bool cards. Existing gateway/classes.rs:105 enforces full versus watch by method classification; preserve that boundary and authenticated actor provenance for answers, never caller-supplied surface.
