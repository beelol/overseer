# Auto Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Meet every core acceptance criterion in the full Auto Mode RFC through local, evidence-backed implementation and verification. AUTO-AC-30 may be verified or explicitly deferred with no extractor shipped.

**Architecture:** Keep account identity, process supervision, and workspace ownership in Overseer. Add a provider-neutral route/observation model, local usage learning, bounded selection and delegation, and an optional XCB integration only where tested ownership boundaries permit. A daemon decision log drives the VS Code Auto UI and verification ledger.

**Tech Stack:** Rust 1.89 Overseer daemon, SQLite, JSON-lines daemon protocol, JavaScript VS Code extension, existing fixture and packaged UI tests. XCB 0.8.10 at `9b3590241f1faf15d669ad46bfde65467fda14d2` currently requires Rust 1.97.1; adoption must resolve this gap without silently raising Overseer's toolchain floor.

**Spec:** `docs/rfcs/auto-mode.md` (the complete 41-criterion local RFC).

## Global constraints

- Account/subscription authentication only; do not introduce an API-key fallback, credential export, automatic purchases, reset redemption, or permission relaxation.
- No hosted telemetry, separate deployment, telemetry API key, or paid calibration work. Learn from actual authorized runs in local SQLite.
- Auto selection is repeated per work unit, including healthy services. Existing manual behavior is unchanged while Auto is disabled.
- Unknown health, quota, and consumption remain unknown. Cost heuristics and token totals are not subscription allowance.
- One authority for each account, process, and workspace. Preserve the existing supervisors and single-writer guarantee.
- Keep implementation local until the RFC acceptance criteria are verified. The owner has requested a draft PR once the work is complete; no remote XCB fork or production deployment is authorized by that request.
- Do not check off a criterion before its named verification scenario and coverage level have evidence at the tested revision.

## Review focus

1. Two harnesses share a quota pool: an account limit must block both, with no false new capacity.
2. A tool's response is lost after an external effect: fallback must pause without repeating the action.
3. Concurrent use on another machine rounds or delays allowance data: learning must not attribute its delta to a local model.
4. The daemon restarts during dispatch or handoff: one writer and one result remain.
5. A model supports text but lacks the browser tool: task-aware routing must exclude it even if inexpensive.

## Execution and completion

Work in the isolated Auto Mode worktree. For each task: read this plan and the RFC, write a test that fails for the required behavior, implement, run focused tests, record the tested revision and evidence, and update only criterion statuses actually proven. Use an isolated Cargo target directory if the worktree path is not writable by the restricted test runner. Daemon process/socket tests require an execution environment that permits spawning and local sockets; a sandbox failure is environmental evidence, not a product regression.

The goal remains active until all 40 core criteria are verified and AUTO-AC-30 is verified or explicitly deferred with no extractor. Neither a green subset of tests nor an implemented-looking diff establishes completion. Once complete, prepare and open the requested draft PR, with the full RFC and verification evidence included.
