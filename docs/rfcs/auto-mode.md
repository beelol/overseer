# RFC: Auto Mode — continuous task-aware agent selection

Status: **draft for discussion; no implementation authorized by this RFC**.
Requested by the owner on 2026-09-25. Baseline: `2c2c7cf`. Revised after owner feedback: continuously assign the right model/effort to each work unit; no user-maintained routing policy; prefer evaluating XCB reuse or a pinned fork.
Acceptance criteria: **0 / 36 verified**, tracked independently below as `AUTO-AC-NN`.

## Outcome

A user chooses **Auto** and Overseer repeatedly assigns the next task or subtask to a strong, suitable agent at a sensible reasoning effort, using current account allowance and expected consumption. Auto is ongoing work allocation, not merely initial selection or outage failover. It can change agents while every service is healthy.

The owner's example is the required product behavior: a frontier agent identifies a browser run-through as a bounded task and dispatches it to Sol at medium reasoning; the result returns to the parent, which may use a stronger model for a difficult diagnosis and another suitable route for the following step. These names illustrate the behavior, not permanent model choices or an instruction to always use a frontier coordinator.

A route is **harness + provider endpoint + account + model + reasoning effort + capabilities**. Choose the model/effort that fits the work and then a compatible available harness, subject to a user's optional harness preference. OpenCode can expose several provider routes; changing harness while retaining the same unavailable upstream does not solve an outage.

Success means completing useful work with strong task-appropriate models without needlessly burning scarce subscription allowance. Neither the most expensive model for every step nor the cheapest model regardless of suitability achieves that. The user need not maintain provider rankings, model weights, reserve percentages, or a routing run file. Optional harness preference and explicit manual pins remain available.

The selector needs three different facts: what this work requires, what each route is expected to consume, and what the account has left. Provider/harness telemetry should supply the measurable facts; bounded inference may assess task difficulty and suitability. Estimates remain estimates, and no model can invent a missing account balance.

## Scope and coexistence

This PR adds this RFC only. It does not change the daemon, extension, account credentials, packaging, original RFC, or release acceptance ledger. Implementation follows a reviewed revision of this document in separate PRs, coordinated with the VS Code production-readiness work.

The design builds on [account governance](account-governance.md), [credential isolation](claude-credentials.md), the [existing RFC](../overseer-rfc.md), and [adapter capabilities](../compatibility.md). Preserve account/subscription login only and no API-key fallback. Auto Mode is disabled by default. Existing manual tasks retain their selected route and behavior.

Current account governance restricts OpenCode to local providers. The routing model must accommodate multiple providers, but cloud OpenCode routes stay ineligible until their account integration is separately supported and verified. Auto Mode does not implement that login work or assume that a ChatGPT/Claude subscription authorizes another harness to use it. A verified local endpoint is a valid route without a subscription quota; this is explicitly `not_applicable`, not an invented unlimited balance.

In scope: repeated task/subtask selection, model and reasoning choice, allowance and consumption observations, bounded task-suitability inference, deterministic eligibility checks, bounded fallback, safe continuation, explanations, and evidence. Out of scope: broad model-quality benchmarking, races between agents, automatic merges, credential migration, purchases, credit redemption, paid overage activation, and implementing a new harness. Native children remain under their harness unless an explicit supported delegation hook routes their work through Overseer; do not claim to intercept every harness-native child.

## Approaches considered

| Approach | Benefit | Limitation | Decision |
| --- | --- | --- | --- |
| User-maintained preference chain or routing file | Simple to implement | Makes the user maintain model economics; cannot adapt to the next piece of work | Reject as the product model |
| Adaptive task allocation using provider/harness observations and bounded suitability inference | Chooses useful capability per work unit and improves consumption estimates | Needs provenance, uncertainty handling, and outcome evaluation | Recommend |
| Inference decides everything from raw logs | Flexible | Can invent balances and bypass eligibility constraints; may cost more than it saves | Reject unrestricted authority |

Provider-specific protocol knowledge belongs in adapters. Deterministic checks enforce account, capability, allowance, and permission constraints. A bounded planner/classifier can propose task requirements and model/effort selection within the eligible set. Implementation constants and versioned built-in defaults are inevitable, but are maintained by the product and tested; they are not a user-authored routing policy. Automatic updates to observed catalogs and local estimates are durable application state, not an editable run file.

### XCB: preferred reuse investigation

The owner prefers using XCB where it works, including an internally maintained fork if adaptation is needed. Evaluate that before building duplicate collectors and routing infrastructure. This documentation PR does not create a remote fork, install it, or change credentials.

Inspected source: [hraness/xcb at `9b3590241f1faf15d669ad46bfde65467fda14d2`](https://github.com/hraness/xcb/tree/9b3590241f1faf15d669ad46bfde65467fda14d2), workspace version 0.8.10, MIT license, Rust requirement 1.97.1. This supersedes the earlier AC-03 snapshot for this investigation. Source findings, not runtime validation:

- [`codex.rs`](https://github.com/hraness/xcb/blob/9b3590241f1faf15d669ad46bfde65467fda14d2/crates/xcb-runtime/src/codex.rs) implements metadata-only `account/rateLimits/read`; [`claude.rs`](https://github.com/hraness/xcb/blob/9b3590241f1faf15d669ad46bfde65467fda14d2/crates/xcb-runtime/src/claude.rs) parses structured rate-limit events. [`usage.rs`](https://github.com/hraness/xcb/blob/9b3590241f1faf15d669ad46bfde65467fda14d2/crates/xcb-core/src/usage.rs) distinguishes fresh percentages from known exhaustion until reset and scopes supported account-wide windows. Unknown/model-specific buckets still need evaluation.
- [`routing.rs`](https://github.com/hraness/xcb/blob/9b3590241f1faf15d669ad46bfde65467fda14d2/crates/xcb-runtime/src/routing.rs) selects models/efforts using relative quality/cost/latency profiles. Those numeric profiles are hand-authored heuristics, not measured subscription consumption. Its large-prompt frontier preference is not sufficient evidence that a long browser checklist requires the most costly model.
- [`task_classifier.rs`](https://github.com/hraness/xcb/blob/9b3590241f1faf15d669ad46bfde65467fda14d2/crates/xcb-runtime/src/task_classifier.rs) supports bounded capability classification with deterministic fallback. Its fitted model predicts historical operator choices; it is not a verified model-quality benchmark.
- [`route`](https://github.com/hraness/xcb/blob/9b3590241f1faf15d669ad46bfde65467fda14d2/docs/route.md) is a one-turn contract with admission/custody/settlement ownership; the caller owns repeated work allocation. Its provider set does not establish OpenCode support. Native process ownership, available tools, context transfer, interactive permissions, and read-only preview behavior must be tested against Overseer's requirements.

Preferred decision order: reuse suitable pinned components or a bounded read-only selection/telemetry surface; if required changes are small, use a pinned maintained fork; use the full runtime only if its ownership contract fits. Keep one authority for each account/process/workspace, with an explicit bridge rather than competing locks. Before adoption, run relevant tests and tiny permitted integration probes, verify packaging/toolchain compatibility, retain MIT notices, document upstream SHA/patches, and provide rollback. A fork should replace unsupported cost assumptions with evidence-backed estimates where feasible and add required provider support; pinning heuristics alone does not solve the measurement problem. If no integration passes these gates, document concrete blockers before implementing an alternative.

## Observation contract

The daemon owns collection, decisions, and durable history. The extension displays those decisions. Conceptual types below are contract requirements, not a proposed rewrite of existing storage.

| Record | Required fields / meaning |
| --- | --- |
| Route | Stable route ID; harness and transport/version; provider endpoint/product; account identity fingerprint; model and reasoning effort; capabilities; enabled/allowed flags; quota-pool IDs where known |
| Observation | Kind, scope, normalized value, source, capture time, original observation time if cached, expiry, adapter/version, evidence reference, confidence (`reported`, `parsed`, `inferred`) |
| Health | `healthy`, `degraded`, `unavailable`, or `unknown`; separate scopes for local harness, endpoint/product/model, account authentication, and local connectivity |
| Quota window | Pool/bucket ID, account/model scope, unit, remaining or used fraction when supplied, limit when supplied, reset time when supplied, and `available`, `low`, `exhausted`, `unknown`, or `not_applicable` |
| Consumption estimate | Model/effort/harness/version, account/plan/window scope, task/context characteristics, estimated allowance draw with uncertainty, sample count, provenance, observation age, and outcome evidence |
| Work unit | Task/subtask ID, parent/dependencies, goal, completion criteria, required tools/context, ownership, bounded execution budget, and result reference |
| Decision | Work-unit ID, selector/estimator version, candidate snapshot, exclusions, model/effort choice, reasons, evidence/uncertainty, reservation, bounded budget, and attempt count |

Keep rate-limit throttling, exhausted allowance, expired authentication, network failure, and ordinary task/tool failure distinct. One failed account does not establish a provider outage. A 429 needs the provider's structured error/reset/retry evidence before it becomes a quota conclusion. Missing and malformed values are unknown, never zero or unlimited.

Several routes may share one account quota pool: `codex` and `codex-app` do not create two allowances. OpenCode routes sharing the same upstream/pool inherit the relevant exclusion. If cross-harness pool identity cannot be established, mark it unresolved and conservatively avoid treating the alternate harness as new capacity after an account-quota failure.

## Collecting evidence

Use this order per adapter:

1. Supported account-scoped provider usage APIs when available under the existing login, or structured harness protocols/CLI JSON/native rate-limit events exposing provider data. Prefer the supported harness interface when it avoids handling credentials directly. A direct provider API is acceptable only after its supported authentication, account scope, units, freshness, and semantics are established; do not equate an API billing dashboard with subscription allowance or add API-key inference fallback.
2. Deterministic parsing of supported CLI output or a narrowly scoped local status artifact with a known schema/version.
3. Optional small-model extraction from already collected, redacted usage text, only with explicit user opt-in.
4. Unknown, with the reason and the action that could improve it.

Text parsing is acceptable; arbitrary grepping of a whole transcript is not an authoritative balance. Parsers must handle supported output versions, ANSI formatting, percent-used versus percent-left, multiple windows, cached timestamps, and reset time zones. Version/format drift, impossible values, missing units, or conflicting labels produce unknown. Never execute content extracted from a display or log.

Model extraction is **off by default** and separable from core delivery. Consent names the destination provider/account/model, data sent, and a user-approved hard call/token or spend cap. Use the smallest validated model from the allowed set; no hard-coded “tiniest” model claim. Send only a bounded, redacted status excerpt, never prompts, source files, or credentials. The response must cite exact input spans for values and pass deterministic schema/range/unit checks. It can extract “20% left” from text; it cannot infer remaining allowance from token consumption alone. Ambiguous output remains unknown; inferred evidence cannot override an authoritative block. No recursive fallback to other models when extraction fails or its route is unavailable. Revocation prevents further calls.

### Health, freshness, and collection bounds

Proposed internal collection defaults (not user routing controls): 60-second health/quota freshness, 5-second timeout per collector, at most four concurrent collectors, and a 10-second overall decision deadline. Batch duplicate refreshes for a shared account/pool. Collect on demand before launch, consume native updates during runs, and refresh on relevant failures. Do not continuously spend model tokens to check health.

Expired observations become unknown and trigger one bounded refresh. A reset timestamp permits rechecking, not assuming the balance has replenished. Future timestamps, reversed windows, or unreasonable clock skew are rejected. Fresh explicit account exhaustion/authentication failure blocks its scope regardless of a public green status. Fresh route success can outweigh a broad public incident advisory; a matching endpoint failure plus a matching incident excludes the affected route. A status feed alone is advisory/degraded until route-specific evidence establishes unavailability. This prevents a status-page outage from disabling working accounts.

No paid synthetic request is allowed just to probe a service unless the user enables a separate bounded probe policy. The actual requested task may be the first request under unknown health. A local network outage is surfaced as connectivity failure and stops repeated remote fallback attempts; an eligible local route can still be considered.

## Measuring model and reasoning consumption

Remaining account allowance and the expected cost of a proposed work unit are separate inputs. Prefer provider-reported per-model/effort allowance rates or charges if they exist for that account/plan. Otherwise collect actual turn tokens (including cache/reasoning where exposed), elapsed time, model/effort, harness/version, context size, and before/after account-window observations from ordinary authorized work. Public API dollar prices are not subscription multipliers.

Only attribute a window delta to a work unit when observations are comparable and attribution is credible: same account/credential generation, same window/reset and plan, settled reporting, no known overlapping work, and enough precision. Reset boundaries, external usage, concurrent tasks, delayed updates, or coarse rounding make deltas ambiguous. Preserve an interval or reject the attribution; zero visible change is not free execution. A local single-writer lock cannot prove that another machine is idle. Prefer authoritative per-request charges over inferred deltas whenever available.

Maintain local estimates keyed by actual model and effort, relevant task/context class, harness overhead, and account/plan semantics. Include failures, retries, and verification cost when estimating consumption per completed work unit. Do not pool different subscriptions or infer comparative quality just because an expensive model was chosen. Invalidate or widen estimates on model/version/plan changes and stale evidence. Learn passively from work the user already requested; no hidden benchmark spending.

Cold start must work without a user-maintained table: discover eligible models and efforts, use the harness/provider's recommended general-purpose default within the task's required capability tier, and show consumption as uncalibrated. Bounded inference can assess task suitability, but may not manufacture a numeric usage multiplier. An unseen premium/high-effort route is not automatically preferred over a suitable default. If no credible suitable route exists, explain the uncertainty and offer a manual choice. Exact adequacy thresholds and estimator formulas are an implementation feasibility result, to be selected and frozen against the evaluation fixtures before claiming completion.

## Continuous task allocation

The normal user choice is **Auto**, optionally with a preferred harness. Accounts/providers authorized for the task remain explicit boundaries. A preferred harness is a soft tie-break among similarly suitable routes; a separate explicit manual pin is a hard constraint. No setup of a provider priority list, quota reserve percentage, or evolving routing file is required.

The task coordinator proposes bounded work units with a goal, completion criteria, required tools/context, and result contract. Reuse an existing capable parent/coordinator when practical; do not run a frontier planning turn for every tool call. A coordinator is itself a metered work unit whose model and effort can be reassessed at checkpoints. A bounded classifier/planner can assess the next unit when the parent supplies no usable assessment. Auto activation discloses that this routing inference consumes allowance on the task's authorized accounts; text-extraction consent remains separate. Charge all planner calls to the task budget.

At initial launch, before dispatching each unit, after a result changes the plan, and on health/quota/capability changes:

1. Refresh relevant evidence within the collection deadline. Enumerate eligible model/effort/harness/account combinations. Enforce allowed accounts, tool/context support, pins, permission boundaries, known exhaustion, and process/workspace constraints first.
2. Assess the unit's required capability. A routine browser run-through can use a strong general-purpose model at medium reasoning if it has the required browser tools and context; a difficult diagnosis may justify a frontier model or higher effort. Long instructions alone do not establish difficulty. A cheap local model lacking the required capability cannot win merely because quota is not applicable.
3. Estimate allowance needed to complete and verify the unit, including coordinator inference, retries, context transfer, cache loss, and harness overhead. Use uncertainty-aware per-window estimates and remaining allowance/reset horizon. Reject a route when a credible bounded work estimate cannot fit its limiting window; no fixed user-managed 10% reserve is required. This admission estimate is not a promise that future token use is exactly predictable.
4. Among credible task-suitable routes, prefer the one expected to complete the unit with less scarce allowance consumption and acceptable quality. Retain meaningful quality gains for genuinely difficult units; do not minimize token count at the expense of correctness. Cross-provider comparisons use expected completed work and each account's limiting-window capacity, not raw percentage or dollar equivalence. Uncalibrated routes use the disclosed cold-start behavior, not a fabricated precise score.
5. Persist the decision and atomically admit the work unit through the existing execution boundary. Account for in-flight commitments to shared pools, revalidate identity and observations, and honor the workspace single-writer lock. Release reservations when work settles and reconcile them after restart; other clients' spending can still change available allowance.
6. Validate the result against the work unit's completion criteria, return it to the parent, record actual usage/outcome evidence, and reassess the next unit. A confirmed capability shortfall can cause a bounded model/effort escalation; a failing test alone is not evidence the model is incapable. Never escalate a permission denial or refusal into another agent to bypass it.

Unknown allowance is not free or exhausted. Prefer a similarly suitable route with credible evidence, otherwise allow one bounded cold-start work unit on an authorized account with its uncertainty visible. If no safe suitable route exists, pause and explain. A later task failure updates evidence; it does not retroactively make an estimate authoritative.

Routing uses a bounded parent budget and per-unit bounds, including planning, execution, verification, retries, and extraction where enabled. Before dispatch, supported transports must enforce the chosen wall-time/turn/token bounds and account for in-flight work; if precise token control is unavailable, disclose it and use supported bounded controls. Default budgets and escalation limits are product-maintained and visible, with user override optional. No autonomous cycle of judge calls, recursive delegation, or spending to learn prices is allowed. Propose at most one routing-classifier call per unit and two capability escalations per unit; provider-failure attempts remain separately bounded below and all share the parent budget.

Reassessment does not require a different model every time. Keep a suitable executor when the expected benefit of switching does not cover handoff/cache cost. Conversely, do not wait for an outage to move routine work to a more efficient executor. Debounce repeated observations; fresh material evidence can change the next dispatch, not repeatedly restart the same healthy work.

### Delegation boundary

Expose an explicit structured delegation interface for coordinators: submit a work-unit description and constraints, receive an execution/result handle, and return the verified result to the parent. Every child records parent ID, route/model/effort, usage, completion status, and evidence. Independent read-only or isolated-worktree children may run concurrently within account budgets; two writers cannot own one workspace. Parent cancellation propagates to unsettled delegated children and results cannot arrive twice after recovery.

Where a harness has a supported native delegation hook, adapt that hook and preserve native child visibility. Otherwise use an Overseer-managed child through the existing harness launch path. Do not silently rewrite native children or claim arbitrary per-tool model switching. First prove tool availability and context transfer for a real browser work unit; the owner example is a release acceptance requirement.

Distinguish delegation from replacement: a parent may wait while a cheaper child performs a browser check and then consume its result. Replacing an executor's ongoing work or moving the coordinator requires the safe handoff rules below. Auto authorizes routine selection for new work units inside its account boundary; post-effect replacement uses the continuation consent and settlement rules.

## Fallback and continuity

Before a task can have effects, a confirmed launch/provider failure can trigger reselection within the same task/account constraints. Proposed limit: three distinct route attempts per dispatch, never retry the same blocked pool through another harness. Respect `Retry-After`; otherwise use a 60-second cooldown for transient endpoint failures. Quota blocks persist until their reset followed by refresh, or fresh authoritative evidence clears them; auth failures require refreshed identity/status. Passing a cooldown permits one shared recovery check, not a stampede. Provider recovery alone does not interrupt active work; the next work-unit decision considers the newly available routes.

Once a run has started, absence of an observed tool call does not prove absence of effects. Continue automatically only after a supported no-effects result or a safe checkpoint: the previous supervisor and writers are confirmed stopped, pending tools/children are settled, workspace ownership is released, and any external action has a known outcome. If that cannot be established, pause with an explanation. Never rerun an uncertain shell command or external action merely because its response was lost.

At a safe checkpoint, if the user enabled continuation, create a new linked run on the same task/workspace with a new harness-native session. Preserve files, snapshots, original goal, user corrections, completed/remaining work, tests, and any unresolved actions in an explicit handoff record. Transfer only context allowed for the new provider. If the handoff cannot fit or required context is unavailable, pause; do not silently discard it. Native session IDs and tool messages are not portable. Label context loss and retain the earlier transcript. The new run inherits equal or stricter sandbox/approval requirements; pending approvals are not transferable and are never auto-approved. If continuation is disabled, offer the prepared switch for user action.

Ordinary test failures, tool exits, refusals, user interruption, and permission denial are not service outages and do not cause outage fallback. Capability escalation is a separate bounded decision based on a verified unmet requirement, never a way to evade permissions or refusals. Disabling Auto stops new automatic dispatch/reselection but does not kill a running agent; queued units pause for manual handling. On daemon restart, reconcile real supervisor state before deciding anything; never relaunch a possibly active run.

## Integration boundary and UI

Implement collection and selection behind a small daemon routing interface after the production branch stabilizes. Existing adapter events feed normalized observations. Account governance remains the identity/credential owner; the supervisor remains the process owner; existing workspace ownership remains the single-writer authority. Additive durable decision records and protocol capability negotiation must let older clients continue manual use. Do not choose a new migration number or refactor shared run/account types in this RFC PR.

New Task offers Auto beside manual selection. Preview the selected harness/provider/account/model/effort and the next work unit, with a short reason such as “Browser check → Sol, medium: suitable tools and lower expected allowance use.” Show parent/child results and escalation reasons, as well as outage reasons where relevant. Show unknown or stale data explicitly. The task history records each switch, trigger, source age, and context limitation. The explanation view shows rejected alternatives, expected versus observed allowance consumption, uncertainty, and the reason for the model/effort choice. It offers a harness preference or manual override, not a routing-policy editor. Monitoring and bounded decisions continue when VS Code closes; UI disconnection must not duplicate execution.

### Evidence and boundaries

- [ ] **AUTO-AC-01 — Isolated delivery.** Auto ships disabled by default and manual routing remains unchanged. **Verify:** diff review plus manual create/follow-up/interrupt regression with Auto disabled; confirm release AC IDs and account-governance work are untouched by routing-only changes.
- [ ] **AUTO-AC-02 — Capability and metering survey.** Record versions, account APIs/harness sources, supported models/efforts/tools, and whether each exposes remaining allowance, actual charges, or only activity. **Verify:** Read-only versioned probes for supported harnesses/accounts; record authentication method and freshness; missing per-model multipliers remain unknown, not a claimed integration.
- [ ] **AUTO-AC-03 — Provider-neutral eligibility.** Common eligibility checks accept provider/harness/model data independently of routing preferences. **Verify:** Synthetic providers pass the same eligibility path; no provider-specific fallback chain; separate adapter knowledge from measured estimates and bounded task inference.
- [ ] **AUTO-AC-04 — Distinct routes and shared pools.** Account/model/endpoint scopes and shared quota are preserved. **Verify:** exhaust one account across two harnesses; both are excluded while an independent allowed account remains eligible; test unresolved identity conservatism.
- [ ] **AUTO-AC-05 — Codex remaining allowance.** Structured account-scoped reads/updates expose all applicable limits independently of consumed tokens. **Verify:** tiny live isolated-account read plus fixtures for multiple buckets/windows, absent fields, exhausted secondary window, and unsupported schema; no fabricated total token allowance.
- [ ] **AUTO-AC-06 — Claude structured acquisition.** Collect supported native events/status data or explicit unknown without a hidden inference probe. **Verify:** Live available-account observation during an authorized tiny task plus versioned fixtures; test pre-response absence, missing windows, original cache age, and preservation of existing status-line settings.
- [ ] **AUTO-AC-07 — OpenCode provider separation.** Each supported provider route has its own evidence and authentication eligibility. **Verify:** real OpenCode with two controlled local endpoints; failing one leaves the other eligible; stats-only data stays quota-unknown; unsupported cloud login is excluded.
- [ ] **AUTO-AC-08 — Parser honesty.** Deterministic collectors fail safely on format drift. **Verify:** fixtures for ANSI text, used/remaining inversion, localization, malformed/negative/out-of-range values, reset time zones, and missing units; unknown replaces invented balances.
- [ ] **AUTO-AC-09 — Scoped health.** Public incidents, route errors, authentication, throttling, and local connectivity remain distinct. **Verify:** decision fixtures for green feed plus exhausted account, unrelated incident, broad incident plus route success, matching endpoint failure, 429 without quota proof, and offline host with local alternative.
- [ ] **AUTO-AC-10 — Freshness and reset.** Expiry/reset schedules a bounded refresh instead of assuming health/capacity. **Verify:** fake clock tests at expiry/reset, cached source timestamps, clock skew, out-of-order updates, and collector timeout.

### Decisions and resource bounds

- [ ] **AUTO-AC-11 — Constraints and harness preference.** Account boundaries, tools/context, permissions, and explicit pins are enforced; optional harness preference is soft. **Verify:** A preferred but incapable harness loses to an eligible one; an explicit pin is respected; browser tool absence, unsupported effort, and permission downgrade exclude routes.
- [ ] **AUTO-AC-12 — Task-aware model and effort.** Healthy services can yield different choices for different work units. **Verify:** A browser-check fixture chooses a suitable strong general-purpose model at medium effort; a diagnosis fixture with demonstrated higher requirements chooses a stronger model/effort; no provider ordering file is supplied.
- [ ] **AUTO-AC-13 — Expected allowance fit.** Estimated unit consumption is checked against every applicable account window with uncertainty. **Verify:** An expensive route fails fit while a suitable efficient route fits; include shared/model-specific windows, coarse precision, unknown draw, and a reset boundary; no fixed user-maintained reserve or raw cross-provider percentage comparison.
- [ ] **AUTO-AC-14 — Unknown and cold start.** Auto works without measurement history while exposing uncertainty. **Verify:** First-run discovery selects a suitable supported default; absent usage is not free; unsupported tools still exclude; an inference response cannot turn unknown balance into a fact.
- [ ] **AUTO-AC-15 — Reproducible decision trace.** Record work-unit requirements, observations, inference output, estimator version, selected model/effort, and explanation. **Verify:** Replay identical recorded inputs, including any inference result, to reproduce a decision; do not claim new model calls are deterministic; inspect exclusions and uncertainty without secrets.
- [ ] **AUTO-AC-16 — No suitable route.** No eligible capable route within the task bounds means no launch. **Verify:** All unavailable, exhausted, incapable, or credibly unaffordable cases pause with reasons and refresh/manual actions; no repeated inference or unapproved spending.
- [ ] **AUTO-AC-17 — Concurrent admission.** In-flight allowance commitments and workspace ownership are atomic across parent/children. **Verify:** Concurrent requests cannot over-admit known budget or share a writer; a competing manual run and pre-launch identity change are handled; failed launches release commitments and external usage remains uncertain.
- [ ] **AUTO-AC-18 — Bounded collectors.** Collection obeys timeout, concurrency, deduplication, and no-paid-probe defaults. **Verify:** 100 synthetic candidates with stalled collectors reach a decision/pause within the 10-second deadline plus 1-second test tolerance, no more than four collectors run, and duplicate pool reads coalesce; measure UI responsiveness.

### Fallback and continuity

- [ ] **AUTO-AC-19 — Pre-effect fallback.** Confirmed safe launch failure selects another eligible route. **Verify:** preferred route rejects before work; eligible alternate runs; an OpenCode route on the same failed upstream does not evade its exclusion.
- [ ] **AUTO-AC-20 — Bounded retries and stable dispatch.** Failures and reevaluation do not oscillate or multiply execution. **Verify:** exercise Retry-After, 60-second transient default, three failure attempts, shared recovery checks, and no interruption merely on recovery; next-unit selection still evaluates recovered routes.
- [ ] **AUTO-AC-21 — Safe handoff.** Automatic continuation preserves work and transfers only at a confirmed checkpoint. **Verify:** controlled real harness processes fail after a file edit, settle, and continue in a new linked run with the same file/snapshot history and one writer; handoff includes goal, corrections, progress, tests, and limitations.
- [ ] **AUTO-AC-22 — Uncertain effects stop.** Unknown process/tool/external-action outcome cannot trigger replay. **Verify:** lost connection after a mock external side effect, live child process, pending approval, and unconfirmed supervisor stop all pause without a duplicate command or second writer.
- [ ] **AUTO-AC-23 — User intent survives.** Interrupt, denial, ordinary task failure, and disabling Auto do not trigger unwanted fallback. **Verify:** each event leaves the task stopped/failed or the current run continuing as appropriate; continuation-disabled mode waits for user action; sandbox and provider-sharing constraints survive handoff.
- [ ] **AUTO-AC-24 — Durable recovery.** Restart/reconnect preserves decisions without duplicate work. **Verify:** crash before launch, after reservation, after spawn, and during handoff; reconcile actual supervisors and recover stale reservations; reconnect two UI clients with one launch and one decision history.

- [ ] **AUTO-AC-25 — Simple Auto UI.** Users can enable Auto and see ongoing delegation, model/effort choices, usage, and reasons without configuring routing rules. **Verify:** Packaged VS Code flow with no routing file: parent dispatches a browser check, receives its result, and assigns the next unit; unknown/exhausted states, optional harness preference/manual override, and window reopen remain understandable.
- [ ] **AUTO-AC-26 — Credential/privacy boundary.** Observations and handoffs expose no credentials and never change login or spending settings. **Verify:** redaction fixtures, bounded retained evidence, linked-account identity change invalidation, and inspection of logs/events/database; no credential export, key fallback, purchase, reset redemption, or permission auto-approval.

### Continuous allocation and measured efficiency

- [ ] **AUTO-AC-31 — Repeated delegation while healthy.** Selection occurs for every new task/subtask and relevant plan update, not only after errors. **Verify:** an actual parent delegates a bounded browser run-through to a different model/effort with compatible browser access, receives evidence, and routes the next unit independently while both providers remain healthy; fixture the owner's Astra-to-Sol-medium example without hard-coding those names as policy.
- [ ] **AUTO-AC-32 — Consumption attribution.** Estimates use direct provider charges where possible and uncertainty-aware measurements otherwise. **Verify:** clean observations produce a scoped estimate; overlapping/external work, delayed/rounded meters, resets, missing effort, and plan/model changes reject or widen attribution; zero visible delta is not zero cost; no synthetic paid calibration loop runs.
- [ ] **AUTO-AC-33 — Outcome-aware selection evaluation.** Selection preserves a strong task-appropriate capability level and accounts for total completion cost. **Verify:** freeze a versioned held-out task set, quality rubric, reference baseline, and numeric quality/cost tolerances before evaluation; demonstrate useful quality on browser, routine-edit, and difficult-diagnosis cases and lower measured or controlled-fixture allowance cost than always choosing the most expensive eligible route. Include retries/planning/handoffs and label fixture economics; do not claim universal live savings.
- [ ] **AUTO-AC-34 — Bounded routing inference.** Suitability inference is allowed inside deterministic constraints and the task budget. **Verify:** timeout, invalid/injected response, disallowed model, depleted planner budget, and unavailable classifier use a documented fallback or pause; at most one classifier call per unit and two capability escalations; every call is metered and cannot approve tools, invent quota, or recursively delegate indefinitely.
- [ ] **AUTO-AC-35 — Delegation lifecycle.** Parent/child context, result delivery, permissions, and cancellation remain coherent across harnesses. **Verify:** real managed child returns a browser artifact/result exactly once; parent cancellation settles children, restart restores dependency state, concurrent writers are refused, and unsupported native hooks use explicit managed delegation rather than silently intercepting native children.
- [ ] **AUTO-AC-36 — Adaptation without configuration upkeep.** Learned consumption and capability evidence influences later work without a user routing file. **Verify:** controlled history shows one suitable route consuming more allowance and changes a later decision; new model/version invalidates stale estimates; repeated identical signals do not cause churn; expected switching benefit must exceed context/cache overhead; manual override and optional harness preference still work.

## Verification loop and implementation sequencing

Create a separate `docs/verification/auto-mode/` ledger when implementation begins; do not extend the original `records.py` or renumber `AC-01…AC-53` for this milestone. Each AUTO-AC record includes status (`not started`, `in progress`, `implemented / unverified`, `blocked`, `verified`, or conditional `deferred`), tested commit, environment/harness/provider versions, policy/fixture inputs, exact steps, expected and actual result, evidence links, coverage type, and blocker/next action. Only verified receives `[x]`. This RFC is the authoritative checklist until a separately reviewed generator is introduced.

Suggested order: (1) source/measurement feasibility and XCB reuse/fork spike, (2) collectors, consumption estimates, and bounded suitability selection, (3) a repeated parent-to-child browser delegation slice through existing supervisors, (4) admission, handoff, recovery, and UI with tiny live verification, (5) optional text extraction if structured sources leave meaningful gaps. These are slices for a later implementation plan, not tasks dispatched by this RFC.

For a future goal loop: pick an unmet core criterion, implement the smallest related slice, run its Verify scenario and affected regressions, attach evidence at the tested commit, and update its status. Finish only when all 35 core criteria are verified and the optional extractor is verified or explicitly deferred. Missing logins/platforms remain visible blockers or unsupported scope; do not solve them by repeatedly spending tokens. No implementation goal or recurring automation is started by drafting this RFC.

## Review decisions and feasibility gates

Confirmed direction from the owner: continuous per-work-unit model/effort selection; strong models used efficiently; optional preferred harness; no user-maintained policy/run file; provider/harness usage data first; inference where useful; prefer XCB reuse or a pinned fork if it works.

Still to establish through bounded implementation spikes: which installed interfaces expose timely per-model allowance information; how accurately task consumption can be attributed; the simplest XCB integration boundary; and the calibrated task-adequacy/consumption algorithm. These are explicit engineering deliverables, not reasons to ask the user to author routing rules. The implementation plan must freeze evaluation thresholds and default task budgets before the corresponding criteria can pass. No remote fork, production implementation, or implementation goal is started by this RFC revision.
