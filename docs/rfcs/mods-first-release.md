# Overseer Mods: first release and two optional bundles

Draft for owner review, 2026-10-02. This is design and research, not implementation or verified acceptance criteria. No Mods settings, installs, logins, daemons, builds, tests, or paid model turns were changed or run. Proposed bundle content: [Clear prose rules](../design/mods/clear-prose-rules.md); [examples and evaluation](../design/mods/evaluation.md).

## Intended outcome

The owner can install a reusable mod, choose where it applies, see its effect, and remove it cleanly. Two independent bundled options address the present request:

1. **Clear prose** produces concise writing in complete sentences with enough context to stand alone.
2. **Less tool noise** reduces supported tool results before the harness sends them to the model, using an existing external transformer with recoverable evidence.

Both are off by default. Either may be enabled alone or together. “All agents” excludes Overseer's own session; that session has its own binding. A writing mod does not force telegraphic language or a fixed word cap. A compression mod does not lower model quality, change effort, suppress permission prompts, or claim a percentage of the total bill saved.

## What is settled, and what exists

The last two sections of `docs/rfcs/mods.md` supersede its earlier proposal. The owner selected folders with `mod.toml`; per-run delivery; installation of dependencies inside the mod; deletion of everything it installed; programs in any language as separate processes; separate bindings for agents and Overseer; global harness rules ignored unless opted in; repository recommendations later; a read-only phone view; and owner confirmation for installs and code changes. There is no need to reopen those choices.

**Are mods Rust?** The daemon and its adapters are Rust. A prose mod is mostly TOML and Markdown. RTK happens to be Rust; other transformer programs can be Python, JavaScript, or another executable. No mod code is loaded as a daemon library.

This checkout has no Mods subsystem: a search of daemon, extension, TUI, criteria, and ledger found no `mod.toml` or Mods implementation. `daemon/src/adapters.rs` launches harnesses and normalizes their output; `daemon/src/daemon.rs` composes turns, guardrails, channel configuration, and transport requests; `daemon/src/overseer/session.rs` manages the separate session and role tools. These are integration boundaries to reuse, not proof that Mods exists. The daemon's received output is already downstream of the harness's model interaction: shortening it for a view saves no inference tokens.

The local Codex CLI reports 0.158.0. Its `exec --help` confirms `--ignore-user-config` omits config.toml while retaining authentication from CODEX_HOME. `--ignore-rules` omits execpolicy files; it is not a switch for AGENTS.md. The implemented adapter may select a different bundled executable, so qualify that resolved executable, not just PATH. Global instruction and skill suppression, resume behavior, and native-child inheritance need their own probes.

## Recommended delivery

Keep the agreed bundle architecture. Ship the smallest reusable slice in two phases, each with its own criteria and review. Text delivery can be released before a transformer is qualified; the transformer must not be represented as active merely because its card exists.

**Phase 1: library, bindings, Clear prose.** Support bundled versions and importing a local `mod.toml` folder. Separate install from enable, persist bindings for all agents/repository/group/agent/Overseer, resolve conflicts, snapshot the effective set per turn, expose shared daemon methods and a Mods/Applied view in VS Code and the TUI, and show it read-only on the phone. Clear prose is ordinary bundle content, not hard-coded prompt text. Rules and one style are the initial supported kinds; other kinds are parsed and explicitly unavailable. One style per agent, narrower binding wins, narrow off overrides broad on, locked bindings remain owner-controlled. Model/account/harness filters remain simple binding selectors. Repository identity follows all worktrees of that repository.

At launch, prefer tested native instruction channels. Codex exec can receive developer instructions through `-c`; Claude can receive a run-local appended prompt file; OpenCode can receive run-local instructions configuration. These routes must be confirmed on the installed executable and on resume. Generic text uses a visible message preface. Persistent transports show the actual activation point; never advertise “next turn” if the option requires a new thread. Child support is yes/no/unknown per piece until tested. Required pieces exclude incompatible routes instead of silently disappearing.

**Phase 2: isolated programs and Less tool noise.** Install a pinned RTK release and any required dependencies under a mod version directory. Do not run global `rtk init`, Homebrew, global npm/pip installs, or upstream installers that write to owner folders. A release artifact with verified integrity is preferable to building a moving branch. If source build is needed, keep its build environment, caches, dependencies, logs, and outputs in mod-owned storage. Record the exact source/ref, artifact hash, recipe, runtime permissions, and installation tree. Removal during use disables new applications immediately, then retires files after the last referencing turn exits; the card says when cleanup is pending.

Keep this phase limited to one externally executed, reviewed output filter and two result adapters. General marketplace imports, arbitrary MCP servers, native bundles, dependency solvers for every ecosystem, semantic rule conflict detection, full limits, auto-install, repository requests, and cloud proxies follow later. A local mod's unsupported program recipe stays unavailable until its installer/runtime can actually meet the declared isolation.

## Manifest and internal boundaries

Define a versioned manifest with identity/version/source, piece declarations, conflict slots, permitted scopes, and explicit install/runtime permissions. These are separate from owner's bindings. Build a deterministic resolver that returns an immutable turn plan: binding reasons, text digest, program path/hash, adapter/capability version, permissions, applied/pending/unsupported state, and child coverage. Each harness adapter consumes that plan alongside existing daemon-owned guardrails and tool configuration. The adapter never accepts a mod's arbitrary launch flags.

Clear prose provides one style file, `clear-prose-rules.md`, and no program. Less tool noise provides a program, a result transformer, and a short description of when results are compressed and how to retrieve originals. It occupies a transformer slot, not the prose style slot. No model or effort override belongs in either bundle's default.

Installation isolation and execution isolation are distinct. A private folder or Python venv controls where dependencies live; it does not stop code reading credentials. The runtime must launch the filter through an OS-enforced runner with an allowlisted environment, no network, read-only mod binaries, and only a per-turn scratch/output directory writable. A stdin filter does not need repository access or account HOME/CODEX_HOME/CLAUDE_CONFIG_DIR. Install-time network permission is separate and limited to approved sources. Build/install processes receive no harness logins. If the platform cannot enforce the declared access, code pieces are refused with the precise reason; a manifest's words must never be presented as a sandbox.

All transformer stdout is untrusted data. Validate bounded protocol output and reject unknown or permission-related fields. The transformer cannot answer approvals, supply tools, set environment outside its process, alter the model, change role constraints, read another run, or use Overseer's capabilities. Do not share daemon sockets or account tokens. Preserve the existing read-only session and watcher restrictions: text only for those roles initially; their code mod is shown unsupported. More capable roles require a separately approved design.

## Transformer protocol and harness compatibility

Prefer replacing a completed tool result before the next model request. Preserve the original command and its ordinary permission path. Send an external process a versioned record with a tool/call id, command family, stdout, stderr, exit status, and completion/interruption metadata. It returns transformed text plus coverage/omission metadata. The host controls raw-file storage and identifiers. The process's own exit status never replaces the executed command's status.

Archive the original output once in private turn storage, with separate stdout/stderr, exact bytes, original exit status, hash, and call id. The replacement includes a small “compressed” marker and a run-scoped way to read the exact original without rerunning the command. Recovery uses existing permitted file access or a narrowly scoped retrieval method; it never fetches another run's data. Keep output storage bounded under the run's ordinary retention rules; apply normal redaction to anything shown outside the run. A raw evidence archive is not telemetry and is never uploaded by this feature.

The first default policy recognizes structured, noisy successful output only. Leave failed, interrupted, incomplete, unknown, small, or non-UTF-8 output unchanged. Start with successful test summaries and clearly identified repeated progress/log lines only after fixtures prove that outcome, counts, skipped tests, warnings, paths, and relevant diagnostic text survive. Full failure diagnostics stay raw in v1. Exclude code/file reads, diffs, security scans, permission events, exact quotations, and full-source evidence requests by default. No first-N-lines shortcut. If a selected transform is larger, malformed, times out, fails, or cannot preserve required facts, send the original result and record the bypass; never retry the command. Dynamic or mixed output that cannot be classified safely is a bypass.

| Transport | Candidate mechanism | Status and gate |
| --- | --- | --- |
| Claude stream-json | Run-local PostToolUse hook replaces the result with a schema-correct value. | Official docs describe `updatedToolOutput`; probe exact installed version, stdin/output schema, resume, original approval path, hook ordering, and children. Fixture qualification only while paid Claude turns remain prohibited. |
| OpenCode run/serve | A run-local, Overseer-authored plugin uses `tool.execute.after` and calls the filter as an external process. | Official plugin API lists before/after hooks. Confirm the model-visible result is replaced, isolate the filter, and ensure no global plugin/config writes. Its small shim runs inside the harness, never the daemon. |
| Codex exec/app-server | No supported automatic result-replacement adapter claimed in v1. | Current docs require `permissionDecision: allow` with a PreToolUse rewrite; that is not a neutral post-result filter. Hook trust is tied to the definition hash. Do not bypass trust, answer permissions, or misuse a blocking hook for compression. Mark unavailable until a safe, run-local mechanism is proved. Explicit RTK commands may be offered as advisory use subject to ordinary approval; do not label that automatic coverage. |
| Generic | None. | Text works; transformer explicitly unsupported. |

The RFC's `bin/rtk filter` is illustrative, not a confirmed command. Current upstream source exposes `rtk pipe --filter <name>`, which accepts stdin. Qualify and pin a released version that includes it. Existing RTK filters are candidates, not automatically safe under this policy: validate their retained facts or bypass them. A native post-result filter is preferable to rewriting all shell commands, because its executed command and permission request do not change. If another hook transforms the same output, expose the conflict instead of claiming both ran.

## Candidate choice and sources checked

- **RTK: first candidate.** Upstream says it compresses shell output, and its normal auto-rewrite hook bypasses native Read/Grep/Glob tools. Its own token metric estimates bytes divided by four; headline percentages describe shell output, not the bill. The README lists lossy transformations, so broad coverage is unsuitable until qualified. The source exposes stdin pipe filters. These are upstream descriptions, not measurements in Overseer. [RTK README](https://github.com/rtk-ai/rtk), [current command definitions](https://raw.githubusercontent.com/rtk-ai/rtk/develop/src/main.rs).
- **Headroom: later, primarily as an external filter/MCP integration.** Its public source offers library, proxy, wrapping, and retrieval mechanisms. Its normal wrapper may install Serena and register it in user configuration; proxying moves authentication and provider traffic through another process. Neither fits the first slice. Do not infer Codex subscription compatibility from advertised wrapper support. [Headroom source](https://github.com/headroomlabs-ai/headroom).
- **TOON: later, for structured tool data.** It is a serialization format with lossless JSON round trips, strongest for uniform records; deeply nested data may be worse than compact JSON. It can reduce model-facing structured data without dropping fields, but does not automatically intercept a harness. Keep wire protocols as JSON and validate decoder round trips/model task quality before adapting selected payloads. [TOON source](https://github.com/toon-format/toon).
- **Caveman: importable later, not the requested prose default.** The requested result keeps full sentences and context. Clear prose therefore uses explicit rules without deleting articles or imposing fragment-heavy output. No post-generation rewriting service or extra model call is required.

Current harness documentation: [Claude tool hooks](https://code.claude.com/docs/en/hooks), [Codex hooks](https://learn.chatgpt.com/docs/hooks), [Codex configuration](https://learn.chatgpt.com/docs/config-file/config-reference), and [OpenCode plugins](https://opencode.ai/docs/plugins/). The configuration reference documents developer instructions and an optional GPT-5 verbosity override; do not assume every selected model supports that option. All support rows above are proposals with gates, not claims of live qualification.

## Quality and token evaluation

The prose rubric and examples are in `evaluation.md`. A fixture can prove what instructions were delivered; it cannot prove a model writes well. Owner evaluation should compare frozen tasks with the mod off/on using one attempt per condition, the same harness/model/effort and starting state, and the required `gpt-5.6-luna` low setting. Only use an isolated dev daemon and explicit owner-login configuration when the comparison is authorized. No Claude paid check is allowed under the current repository policy. A missed live clause leaves its criterion partial with that gap.

For compression, replay frozen outputs through qualified filters without any model calls. Record raw/transformed bytes, a named tokenizer/count method when available, filter latency, bypass reason, and exact protected-fact assertions. Show local estimates separately from harness-reported usage. A compressed fixture that loses one failure, warning, path, exit code, count, or required quotation fails even if it is much shorter. Retrieve archived originals and verify their byte hashes. Confirm one execution per command, including failure/timeout cases.

For eventual task comparisons, keep model/harness versions, effort, account id, workspace snapshot, prompt/task class, mod fingerprints, outcome, and condition comparable. Record reported input/cache/output/reasoning fields separately where available, plus turns, raw recoveries, total duration, and reported cost. Rules, hook descriptions, retrieval calls, and added prompts count toward the net outcome. Report the observed difference for that workload with sample count, unknown fields, and cache state. Never infer dollars from subscription quota or promise a fixed saving. One controlled fixture family does not establish all tasks.

Metadata remains local and excludes prompts, output bodies, code, credentials, and account login identifiers. Use the existing usage/event storage contract and coordinate with queued telemetry work rather than creating a second account ledger or outbound analytics system.

## Decisions needed

No new architecture decision is needed to finish this design. The owner reviews the proposed first-release scope and prose rules before criteria are added. The open technical gates are adapter qualification and enforceable runtime isolation; unsupported capabilities can be stated clearly without asking the owner to choose implementation details. If they require automatic compression on Codex in the first release, that requirement needs a dedicated compatibility spike before claiming the second bundle can ship there.
