# Local learning storage boundary

Before revision `4f9a618`, Auto learning tables shared the execution SQLite file. They now use a separate rollback-journal file and connection. Exact row caps and retention limit record counts; a database-wide cap on the execution file would still stop event, run, and workspace writes. AUTO-AC-39 needs a learning-specific byte limit, and AUTO-AC-41 requires telemetry pressure to leave durable execution intact.

## Feasibility finding (2026-09-26)

A local SQLite probe used a WAL execution database, an attached learning database with `PRAGMA learning.max_page_count` set two pages above its initial size, an execution insert, and a learning savepoint. The second 3 KB learning-row insertion returned `SQLITE_FULL`; `ROLLBACK TO learning_write` then failed with `no such savepoint`. SQLite had aborted the shared transaction. An attached database on the execution connection cannot provide the required failure isolation merely by wrapping telemetry writes in a savepoint.

The same probe with **two connections** filled a page-capped learning database and rolled back its transaction while the execution connection committed both event rows. Its learning table retained zero partial rows. This is a system-SQLite feasibility probe, not bundled-rusqlite or daemon acceptance evidence.

A second local system-SQLite probe set a 16-page (65,536-byte) limit and committed 100 small updates to one learning row. With WAL, the open database plus sidecars reached 457,136 bytes (including a 420,272-byte WAL); with DELETE journaling, the observed peak was 8,192 bytes. The page limit alone therefore does not bound total WAL storage. This small probe does not prove a rollback journal has a hard total-size bound for arbitrary large transactions.

## Implemented boundary at `4f9a618`

The daemon now uses one execution connection and a separate local learning connection/file. The learning connection alone gets a 128 MiB page-count cap calculated from its page size, uses DELETE journaling, and stores bounded serialized rows. The cap applies to the database file on the daemon connection, not automatically to an external SQLite connection or rollback-journal and temporary files; worst-case total-size bounds remain unverified. A controlled physical full-file test now makes one learning transaction roll back and set `learning_paused` while the execution event completes. Freeing space lets later work record again without replaying the failed sample or model turn. If the learning file cannot open at startup, the daemon keeps its execution store available and reports learning paused; it retries file initialization on restart.

Detailed measurements, daily aggregates, and thread-credit observations now use the learning connection. Keep active run/account-generation evidence and quota observations in the execution connection until their safety and retention lifetimes are specified separately. Bound every serialized learning record and retained row count in addition to the page cap. Use a local file adjacent to the execution database, with owner-only permissions. No telemetry service, network call, inference call, or provider probe is introduced.

Migration retains existing learning rows: it copies legacy rows into the learning database with idempotent keys and commits **there first**; only then does it mark migration complete in the execution database and clear legacy rows. If interrupted before the marker, retrying the copy must not double aggregates. Clearing learning history must leave the migration marker in place so old execution events cannot recreate deleted learning. Existing `:memory:` tests use a separate in-memory learning connection. A durable reset marker hides old-account learning after failed deletion or an unavailable file; recovery clears it before exposing data again.

Before promoting AC-39 or AC-41, still exercise migration interruption, full execution-database safe-stop, and worst-case journal/temporary-file bounds in the bundled SQLite build. Page-cap pressure during a task, aggregate failure and recovery, 30/90-day expiry, exact row caps, explicit export and clear, active-child ownership, and restart have controlled coverage; these do not yet prove the complete Verify clauses. Measure write/maintenance latency at the row and page cap. A SQLite page cap bounds the learning database file; journal and temporary-file behavior must be inspected and documented separately.
