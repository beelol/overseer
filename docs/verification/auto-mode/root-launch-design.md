# Initial Auto launch: route the first coordinator

Status: implementation contract, 2026-09-27. This refines the [full Auto RFC](../../rfcs/auto-mode.md), especially initial selection, AUTO-AC-17, 24, 25, 31, and 40. It does not mark a criterion verified.

## Why this boundary is separate

`auto.dispatch` selects a managed work unit under an existing parent run. `task.create` starts a root task after the caller has named its harness/account/model. The VS Code composer currently sends that manual shape. Setting `auto_routing` on a manually selected Codex parent only equips it to delegate later; it cannot truthfully implement the RFC's initial Auto choice. The child launch intent cannot be reused for a root because its `parent_run_id` is a required foreign key and its Git snapshot belongs to that parent.

## Owner-visible contract

The composer and full New Task form offer **Auto routing** beside manual agent selection. Auto accepts a repository, prompt, workspace mode, allowed account profiles, optional preferred harness or pinned route, and bounded task requirements. The daemon chooses the initial harness/account/model/effort before a model turn. Manual selection remains a separate unchanged request. Auto returns a stable root work-unit ID, selected-route explanation or pause reason, and one task/run handle once created. The UI shows `selecting`, `launch pending`, `running`, `paused`, or `completed` from daemon state. Reopening VS Code or connecting the phone reads that same record; neither client independently estimates allowance or repeats a launch.

The UI must not imply that enabling `auto_routing` on a manually chosen Codex parent selects the initial route. Its switch and Overseer's separate Auto authority level remain independent. A pinned route is a hard constraint; a preferred harness is only a soft tie-break. No user routing file, hosted telemetry, new login method, or paid calibration is introduced.

## Daemon contract

Add a root-specific `auto.start` request and durable `auto_root_intents` record keyed by a caller-generated opaque work-unit ID. Its canonical request hash covers repository identity, starting ref, workspace mode, prompt, allowed profiles, preference/pin, tools, capability/context/approval/sandbox bounds, and budget. The prompt stays in the existing task record after admission; the root intent and local learning tables store only its hash and structured requirements. Repeating the ID with identical inputs returns the same phase/task/run; a changed request fails. The daemon checks the global default-off Auto gate before a new selection and again at admission.

Discovery runs under the existing ten-second decision deadline with at most four collectors and the current account/profile gates. Root discovery uses a canonical repository path for project-scoped tool evidence, without creating a worktree merely to inspect tools. When the caller supplies no structured task assessment, the bounded AUTO-AC-34 classifier may assess the first unit within that same deadline and task budget; if it is unavailable, the decision visibly uses the AUTO-AC-14 cold-start default and unknown fit. Inference cannot authorize a tool, account, sandbox, or quota claim. The chosen route is revalidated in the prepared workspace before its first turn, including account generation, quota, required tools, endpoint, and permission/sandbox bounds. If repository-scoped evidence cannot safely establish a requirement, that route is unknown or ineligible. The selected route uses the same provider-neutral eligibility, health, quota, scoped-fit, and explanation code as child dispatch. Extract that decision pipeline rather than maintain a second policy.

The root decision, intent, shared-pool commitment, planned Git resource, and queued task/workspace/root-run rows commit atomically before any Git or model-process effect. The task row holds the prompt in Overseer's existing execution store, so a daemon restart does not depend on the original client resending it; the root intent stores only the request hash and structured decision. An asynchronous worker performs bounded Git preparation, records the task-start snapshot and process identity before spawn, then starts the selected turn. It rechecks the Auto gate, account identity, quota, pool commitment, workspace ownership, and route capabilities at the last safe boundary. Current-checkout mode reserves the existing single-writer claim in that transaction. A failed confirmed pre-effect step releases its commitment; an uncertain Git or process effect pauses with its journaled resources. Recovery inspects the branch/path, durable run/process generation, supervisor, and turn outcome before doing anything else. It never retries a possibly completed Git or model effect or creates a second root for one ID. A stopped or revoked root cannot admit a later child.

The root intent is separate from `auto_launch_intents`, which remains parent-child specific. Both use one shared pool-admission authority, not two quotas. A root run that can delegate receives the same per-run Auto tool bridge and bounded allowed-profile set. Until a harness has verified runtime tool injection, it may run as a selected executor but must not be advertised as a coordinator that autonomously delegates.

## Current-main integration boundary

Published main is contained in this branch (last integrated 2026-09-27; revisions are recorded in the verification ledger). Gate S's AC-186 and AC-196 make **Auto routing** independent of Overseer's **Auto** authority level. `auto.start` chooses a route for a user-requested agent; it does not grant Overseer permission to steer, confirm a proposal, answer a denied permission, or change a pinned route. The owner has now confirmed that Overseer never answers an agent's permission request by itself, at any authority level. The initial root, a manual `task.create`, a child dispatch, a Swarm worker, and an Overseer-initiated agent or watcher must ultimately compete through the same durable account-pool, agent-slot, and workspace admission. A separate root-only quota or slot counter would fail AC-196 even if its own replay test passed. Gate S owns the request to start or redirect; Auto owns only route selection. A redirect retains its route unless the owner asks to change it, while a distinct next work unit can be reassessed.

Gate S's AC-193 and AC-196 also make watches and Overseer's own turns metered units. With routing enabled, an eligible watcher route may differ from its subject, but its read-only permission and agent identity do not change. Continuity's successor keeps that same agent identity, holds, and watches (AC-197); `auto.start` may not create a second apparent agent during handoff. The extension-owned Talk to Overseer flow (AC-107) currently proposes starts, and Gate S moves the single conversation into the daemon. Either producer must submit one stable work-unit ID to this launch boundary; Auto does not create a second conversation or its own proposal system. Gate N's phone, when it lands, reads the same durable decision after sleep or reconnect rather than selecting a route in the client.

These main changes alter the **integration seam and verification matrix**, not the provider-neutral ranking policy or the local-only usage design. The existing Auto RFC already covers the two switches, metering, pinned routes, denied permissions, phone replay, and shared admission; this contract makes their effect on the new root launch explicit. No new Auto acceptance criterion is inferred, and none is verified by this design.

## Verification sequence

1. A red protocol test calls `auto.start` in a fresh daemon with two healthy controlled accounts and asserts that the initial model/effort, not the client, is selected. It replays the ID, rejects changed inputs, and checks one task, root run, supervisor, and decision event. Manual `task.create` remains unchanged.
2. A controlled discovery test varies tools, quota, preference, and pin. Unsupported browser tools and exhausted windows exclude routes; unknown allowance stays unknown; no profile credential or raw prompt reaches the decision trace.
3. Fault injection covers a second client during selection, a crash before Git, after Git, after run-row commit, and after spawn; each returns one stable record or an effects-uncertain pause. A concurrent manual run, child dispatch, and, when Gate S or Swarm lands, an Overseer/watch or worker launch share pool, slot, and workspace admission. A denied permission cannot be retried by submitting the same work through another producer.
4. Packaged VS Code exercises Auto and manual starts, preview/explanation, pending and paused states, browser child/result/next unit, and window reopen. If Gate N phone control has landed, a sleeping phone and VS Code reopen the same root decision without a second launch.
5. The final live support matrix claims only authenticated routes and coordinator tools actually exercised on the installed harnesses. Controlled fixtures establish safety and idempotency, not real model judgment or subscription savings.
