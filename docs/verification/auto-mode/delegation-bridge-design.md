# Auto delegation bridge: current gap and shared contract

Assessed on 2026-09-27 against `origin/main` at `7bccc3a` and the Auto branch at `c07f4ce`. This is a design and source-inspection record, not verification of AUTO-AC-31 or AUTO-AC-35. No paid model turn or harness configuration change was made.

## What works today

`auto.dispatch` accepts a bounded work-unit request, selects a route, and starts an Overseer-managed child. The daemon stores one child per work-unit ID and emits one `managed_child_result_available` handle when that child completes. `run.result` returns up to 8,192 characters of the child's final assistant output. Controlled fixtures exercise a parent dispatching a browser-labeled unit and then an independently selected diagnosis unit, but the test caller explicitly invokes both requests and explicitly sends the child's text in `run.follow_up`.

The local daemon protocol is an owner-UID Unix socket. Its current `auto.dispatch` request accepts `parent_run_id` from the caller, and there is no per-run tool identity in that protocol. A harness turn with shell access runs as the same UID. Therefore exposing `overseerd ctl auto.dispatch` as the agent's delegation tool would not bind a request to its actual parent run, even though the daemon checks the named parent's state and account. A prompt or repository file must not be able to nominate another run as its authority. An ordinary UI request from the owner and a model's delegated request need distinct provenance at this boundary.

The Gate S Overseer design on main proposes a per-run stdio MCP shim, configured only for the run, with daemon-enforced action levels. Auto should reuse that transport and its run identity, not install a second persistent MCP configuration or create a second admission authority. Gate S's report/ask/claim channel is enabled by default only when multiple agents share a repository. Auto delegation must be granted separately to an Auto-enabled parent, including a lone parent. The installed Claude Code CLI exposes `--mcp-config` and `--strict-mcp-config`; a metadata-only `claude mcp list` call did not test those session flags. The installed Codex app-server accepts per-process configuration overrides: with an isolated temporary `CODEX_HOME`, a minimal stdio MCP server, and no model turn, `mcpServerStatus/list` reported the injected server and its `probe` tool connected with no tool error. This establishes Codex tool discovery, not model use, run binding, or permissions. Claude and OpenCode runtime injection still need controlled probes. OpenCode's selected local-provider configuration must remain isolated from the user's configuration.

## Required contract

1. The daemon creates a private, unguessable capability for a specific parent run and one Auto session. The bridge derives `parent_run_id` from that capability; the model never supplies or changes it. The bridge exposes only delegation and result methods, not the owner-wide daemon RPC surface. Disabling Auto or ending the parent revokes new submissions. Explicit user pins, allowed account profiles, sandbox, approval ceiling, and remaining task budget are enforced in the daemon on each submission. This binds the request to the issued run in the protocol; it does not establish isolation from a malicious same-UID shell process that can read the run's launch data. That threat boundary needs an explicit test or a stronger OS boundary before claiming protection against a hostile local process.
2. `submit` accepts a stable work-unit ID plus bounded goal, completion criteria, required tools/context, and requested budget. It returns the existing durable launch/result handle. Repeating the same ID with identical requirements returns the same handle; changed requirements fail. The bridge cannot widen the parent account set or permissions, and a denied permission cannot be retried through another route.
3. `result` returns `pending`, `ready`, `completed_without_text`, or `not_completed` for that handle. A ready result includes the bounded assistant output, source event sequence, child route/model/effort, workspace/artifact reference, and uncertainty/usage summary. The result is untrusted child content, clearly delimited for the parent. Its event sequence and work-unit ID let a parent resume after a lost tool response without re-executing the child. The existing parent notice remains a content-free UI/recovery signal.
4. A parent may choose another work unit after receiving a result while all providers are healthy. Tool calls do not trigger an unbounded recursive dispatch loop: admission applies the parent's remaining budget, child execution bound, maximum outstanding children, and cancellation. Parent interruption settles or conservatively pauses its children; an unknown external effect never causes replay.
5. The same daemon admission transaction covers model allowance, agent slot, workspace ownership, and launch intent for UI, Auto, Swarm, and Gate S callers. The bridge carries caller provenance into the decision trace, but prompts, source files, credentials, and raw tool output do not enter usage-learning telemetry.

## Verification needed before claiming the behavior

- A controlled parent harness invokes the injected tool itself, requests a browser-capable child, receives its result in the same or resumed parent conversation, and requests a second independently selected unit while both providers remain healthy. Assert the selected child's effective browser tool and a real browser artifact, not merely the phrase “browser check.”
- A forged parent ID or capability, changed work-unit ID payload, disabled Auto, forbidden account, wider sandbox, denial, and exhausted parent budget each refuse before launch. Reconnect and daemon restart preserve one child and one result; parent cancellation leaves no active descendant or duplicate external action.
- Repeat across each claimed harness transport using the installed versions and one tiny authorized live run where the RFC requires it. A fixture proves protocol behavior but does not prove a real model used the bridge or browser.

Until these tests exist, AUTO-AC-31, AUTO-AC-35, and the packaged Auto UI criterion remain in progress. The next implementation slice should establish this shared run-bound tool transport and its negative authorization tests before adding the composer switch or automatic follow-up turns.
