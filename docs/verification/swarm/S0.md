## What now exists

- **Normal launch, daemon:** `swarm.start` (Overseer class: Confirm). With a category, an objective and the repositories it returns a read-back: the approved account pool and its source (`application`, `category`, a one-time `selection`, or a `run` override), each approved target's latest reading (an account profile shows `measured`, `stale`, `unknown`, `allowance_unknown` or `exhausted`, and per window its remaining allowance and the run's share and finishing reserve under the effective percentages), the worker ceiling (`max_workers` against `agents.max_active` less the director's slot), growth per wave, the deadline, the director, the fan-out mode (`bounded`, `serial` when no target has a usable reading, `none` when nothing is approved) and one summary line such as "Auto · up to 4 workers · 60 min". Nothing is written. The owner's yes is the read-back's SHA-256 with a `request_id`; the daemon recomputes the read-back and commits only if it is unchanged, a director is qualified, an account is approved and a slot is free. It then creates the run (replay-safe per request), records the confirmation (`swarm_start_confirmations`, shown as `start` in `swarm.get`), saves a one-time selection as the category's approved pool, and launches the director through `launch_director`: the owner identity, the director's durable app-slot hold and its run bound to the category (the one app-slot count). A repeated yes returns the same run and director.
- **Normal launch, VS Code:** `Overseer: Start Swarm…` (agents view menu and palette): repository (asked only with several), category, objective; accounts only when none are approved; the read-back in one modal with **Start swarm**. A blocked director is reported without asking; a read-back that changed before the yes is shown again.
- **Director choice:** a director needs daemon-issued Swarm tools and enforced descendant control, which no model harness has. Outside the fixture API the start is therefore blocked `no_qualified_director` and no weaker substitute runs. Under `OVERSEER_SWARM_FIXTURE_API=1`, the scripted director named by `OVERSEER_SWARM_FIXTURE_DIRECTOR` is the qualified one.

## Proposed native director (switch `swarm.native_director`; history before 2026-09-28, when it was off by default)

The owner's decisions 1 and 2 (Swarm RFC, "S0 normal start") are pending, so the proposal is built behind a daemon setting that defaults to off. With it off nothing above changes. With it on, the director is Claude Code on the first approved Claude account, qualified by the daemon (installed, version at least 2.1.246, `--help` lists the MCP, allow-list and deny flags), launched through the same `swarm.start` yes and the one launch path, with the director's Swarm tools over Gate S's `overseerd mcp` shim and native `Agent`/`Task` denied. Native Claude workers get the worker's tools over the same transport. The MCP token is the director's owner token or the worker's attempt token, written only into the run's private MCP configuration.

## What S0 still lacks (why it stays partial)

- **A live director.** The owner decided the Claude director (on by default since `e7e9e18c`), but it has run only as the synthetic Claude fixture, whose planning, routing and acceptance are a script, not model reasoning; no live Claude director has run (no paid turns). Its `swarm/director` draw is qualified only from fixture runs; an uncalibrated director still runs unbooked and makes a single Claude account busy for booked workers (`account_pool_busy`). `Agent`/`Task` are denied by argument; no test observes a live Claude refusing a spawn.
- **Booked account workers in S0.** Since `0f38f758` (decision 3) a native Claude worker may join S0's audit read-only, with the post-attempt source check ([SWARM-52](SWARM-52.md)); in these S0 fixtures the only Claude account is the uncalibrated director's (busy, `account_pool_busy`) or has no qualified draw (`upper_draw_unknown`), so S0's workers are still fixture processes that book nothing. Native audit workers run in `native_claude_workers_audit_read_only_and_a_source_change_fails_the_attempt`, not in S0 itself. Native workers now have a report transport behind the switch, exercised in an `isolated` run, not in S0. Booked Claude workers are exercised with `isolated` permission in `shared_launch.rs` (CONTRACT-01). A Claude account can never be calibrated from product readings today (see the Auto RFC's "Claude quota readings for calibration"), so on a real Claude account the read-back is `serial` or `allowance_unknown`.
- **The fixture gates stay.** `swarm.plan`, `swarm.admit`, `swarm.worker.launch`, `swarm.director.*` and the rest of the director protocol remain behind `OVERSEER_SWARM_FIXTURE_API`: lifting them would let an unqualified process direct workers. `swarm.start` is not gated; outside fixtures it stops at `no_qualified_director` unless `swarm.native_director` is on. The switch does not lift these RPC gates: the native director reaches the same transitions only through its own tools, authenticated by its token.
- **Not exercised:** the VS Code command in a real window (no VS Code this session), revoking an approved account during the run, preset edits during the run, Auto × Swarm, more jobs than grid tiles, and any live account.

Required criteria SWARM-01/02/06/12/39/40/59 are unchanged in status except where their records say otherwise; none is checked by this evidence.
