# Swarm implementation milestone 3 — plan revisions

A director can submit a complete revised job plan with an expected run revision and a bounded reason. The daemon validates the DAG, changes the revision atomically, invalidates jobs whose own contract changed and their descendants, and preserves unrelated accepted work. Active affected attempts receive a durable redirect and their old-revision artifacts cannot satisfy the new assignment. An unchanged ready job keeps its original assignment revision even when the run revision advances. After an affected attempt's exit is confirmed, it becomes ready or dependency-blocked under the revised contract, subject to the two-attempt cap.

Evidence: `daemon/tests/swarm_plan.rs` covers the changed interface/active consumer/unrelated accepted case and an unchanged ready job finishing after another job changes. The new test first failed with `unknown method swarm.revise`. After implementation, `cargo test --offline --test swarm_plan` passed all 5 tests and `cargo test --workspace --offline` passed 4 unit, 25 protocol, 5 broker, 5 plan, and 3 state tests.

Remaining limits: the revised input must retain existing job IDs; job removal needs a separate cancellation transition. Redirect is queued, not delivered to a live harness. The public fixture-facing attempt registration and exit confirmation calls still need daemon-owned runtime authority. User-message revision input, retraction propagation, director lease enforcement and conflict resolution remain unimplemented. No full RFC criterion is claimed complete from this milestone.
