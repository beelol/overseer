# Swarm implementation milestone 7 — fixture admission and review pressure

`swarm.admit` is available only with the explicit fixture opt-in. In one SQLite transaction it rechecks an injected target snapshot, run/job revision and state, approved target and required capabilities; freezes each run/pool/window allocation on first use; reserves every applicable window; registers an attempt; and consumes a worker slot and growth-wave position. Stable request IDs prevent replay from duplicating the reservation. Two concurrent socket requests for the same run allocation produce one admission and one block. Different harness targets referencing the same pool share reservation headroom across categories. A later larger snapshot does not expand an already frozen run allocation. Zero or missing upper estimates cannot authorize free fan-out.

The fixture path counts one director slot for a running category, enforces the default eight workers and nine total agents, and admits at most four workers per five-second wave. An explicit 32-worker/33-agent policy admitted 32 fixture attempts in eight waves; the 33rd worker was held. A result report and its `submitted` job state commit together. At eight submitted results, new admissions pause; after five evidence-backed decisions reduce the backlog to three, an admission resumes.

Evidence: `daemon/tests/swarm_admission.rs` first failed because `swarm.admit` was absent, then passed 6 cases covering allocation freeze, request replay, shared pool, concurrent claims, default and explicit ceilings, waves and review pressure. `daemon/tests/swarm_broker.rs` first failed for submitted-state persistence. `daemon/tests/swarm_policy.rs` first failed for a zero-cost estimate. After the fixes, `cargo test --workspace --offline` passed 4 unit, 25 protocol, 6 admission, 7 broker, 3 director, 5 plan, 5 policy, 3 settings and 3 state tests.

This is **fixture admission**, not a live route-to-launch implementation. Auto Mode does not yet supply the snapshot, ordinary non-swarm tasks do not share this reservation ledger, native descendants are not counted, live processes are not launched or reconciled, and reservations remain conservative until actual usage can be measured. The admission RPC is disabled without fixture opt-in. No full RFC acceptance criterion is claimed verified from this milestone.
