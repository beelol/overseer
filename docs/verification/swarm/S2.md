Status: partial. Backend and joined replay revision: `2fecb59`;
persistent lost-ack replay revision: `de0959b`. Fixture:
`fixtures/swarm/ledgerpay-v1/manifest.json` (version 1). Support level: local
FastAPI 0.118.0, PostgreSQL 16 and Redis 7.4; no live billing service, paid
account, model worker or production subscription.

Input: signed local `evt-42` activation payload for `sub-1`, initial grant counter
0, and two delivery IDs in a Redis list. Each K1–K4 probe creates its own
PostgreSQL schema and Redis list. K1 tests signature/ingress; K2 observes the
duplicate queue entries and a lost acknowledgement after a committed update;
K3 runs two deliveries through a concurrency barrier; K4 delivers a version-2
cancellation before a version-1 activation. A separate protected K3 probe
inserts the unique receipt and updates the subscription in one transaction.

Expected: invalid signatures do not create events; the seeded two-delivery
replay increments 0→2 despite one receipt, while the protected variant ends at
1. Stale activation does not overwrite cancellation. After an update commits
but its receipt is absent, the state probe reports an unknown outcome and no
automatic retry. A missing Redis queue remains environment-blocked in Swarm
coverage and cannot be accepted as retry-safe or completed.

Observed: `./run-local.sh` passed seven Python tests against disposable
PostgreSQL/Redis containers. The seeded barrier replay ended at grant_count=2
with one receipt; the protected replay ended at 1 with one receipt. Invalid
signature returned 401, signed ingress 202, stale activation was rejected and
left version 2 inactive, and the lost-ack probe returned
`unknown_do_not_retry`. A Redis failure returned 503; retrying the same signed
event after queue recovery enqueued it once rather than treating the
previously unqueued database record as complete.

`./run-swarm.sh` passed two opt-in Rust tests. The joined run admitted K1–K3
within a three-worker ceiling and initially blocked K4. K2's durable
duplicate-delivery discovery reached a director batch; a targeted K3 advisory
was acknowledged as delivered and applied. After K1's negative-signature
check was accepted and its exit confirmed, K4 filled the slot. K3 submitted
seeded and protected database results as one reproduction artifact; K2's
lost-ack evidence and K4's stale-event result remained separate. A final
director batch was claimed before acceptance, then all four jobs were
accepted with evidence and the scripted audit reached `completed` with four
admissions. A separate missing-Redis probe produced a real 503; Swarm
reported `environment_blocked` for `redis_queue` and rejected both acceptance
and completion.

Replay: in `fixtures/swarm/ledgerpay-v1`, create `.venv` and install the pinned
`requirements.txt` with `uv`, then run `./run-local.sh` and `./run-swarm.sh`.
Both scripts bind disposable containers to random localhost ports and remove
them on exit. The Rust test is ignored by default because the services and
local socket permission are required. These are deterministic fixture tests.

Follow-up `de0959b`: `session.py` holds one PostgreSQL schema and Redis list
across separate processes. It starts with two queued `evt-42` deliveries and
commits one grant without a receipt or acknowledgement. A focused local test
proves a blind second delivery raises the counter to 2. In the joined Rust
replay, the daemon persists `swarm.effect.begin` before the command, loses the
acknowledgement, then restarts. Replaying the same operation returns
`may_execute=false`; a separate Python process queries the real database and
reports counter 1, no receipt and one pending delivery. That observation is
submitted as an `effect_probe` artifact before the director reconciles the
effect as applied. An unrelated K1 signature check is accepted while K2 is
uncertain. Replaying the effect after reconciliation still cannot execute and
the external counter remains 1. `./run-local.sh` passed nine Python checks;
`./run-swarm.sh` passed three opt-in Rust replays against disposable services.
