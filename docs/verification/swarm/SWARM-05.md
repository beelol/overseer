# SWARM-05 — serial versus parallel benefit

Status: partial. Revisions: `1aa56f9` (measured outcomes), `0d2074c` (planned resource independence). Support level: fixture-only, committed benefit decisions, admission gate and measured worker wall time.

Input: two paired plans estimate the same two independent jobs. Each plan supplies planning, context transfer, worker execution, retry allowance, integration and review costs in elapsed milliseconds and native quota units. The fixture compares a 240 ms serial plan with a 210 ms parallel plan, 40 milli-points of allocation and 10 milli-points reserved to finish. Variants increase parallel context cost to remove the time benefit, reduce finishing reserve, exceed total allocation, make the jobs dependent, or make both plans unaffordable. Another fixture removes a phase estimate, changes a job identity, or supplies an uncalibrated worker estimate. Admission fixtures exercise no decision, committed serial and parallel decisions, daemon restart, changed decisions while workers are active, job IDs outside the batch, and a second batch after two workers submit accepted evidence and exit. A supervised `/bin/sleep 1` worker supplies a measured terminal run timestamp, followed by another daemon restart. Existing 32-worker, review-pressure, scheduler, dispatch, context and outage fixtures now declare synthetic beneficial batches when they expect concurrent admission.

Expected: choose parallel only for independent jobs with a strict time benefit, affordable total usage and enough finishing capacity. Prefer serial on ties. Reject incomplete or inconsistent estimates. An unproven run must not fan out; a committed decision must survive restart and bound the specific batch without bypassing quota, worker or global ceilings.

Observed: `swarm.benefit.preview` selects the two-worker parallel plan with a recorded 30 ms expected gain, 35 milli-points total usage and 10 milli-points finishing cost. It returns serial when coordination erases the benefit, reserve or allocation is insufficient, or jobs are dependent; it reports blocked when neither path is affordable. Malformed estimates fail. A fixture-only `swarm.benefit.commit` persists the effective estimate and decision by plan revision and wave. With no decision, the second active worker is blocked. A serial decision holds it too; a parallel decision admits only estimated jobs up to its recorded batch size, subject to the existing quota and concurrency checks. The decision and replay survive daemon restart. A changed decision cannot replace an active batch; after accepted workers exit, the next ready batch receives wave 2 and is admitted. Each admitted attempt retains its estimated elapsed time and native-unit usage. After a supervised exit, the daemon records measured run wall time atomically with exit confirmation; `swarm.get` exposes that measurement after restart. Native-unit actual usage remains null because no authoritative provider receipt exists. A new fixture declares overlapping planned write claims, restarts the daemon, and supplies an optimistic independent parallel estimate. The committed choice is serial with `resource_conflict`; read-only overlap remains available to the admission claim rules. The existing commit replay still succeeds after workers leave `ready`. The full offline Rust suite passed 152 tests (10 unit, 49 protocol, 93 Swarm) at `0d2074c`.

Commands: `cargo test --offline -p overseerd --test swarm_benefit -- --nocapture`; `cargo test --workspace --offline -q`.

Evidence: `daemon/tests/swarm_benefit.rs`, `daemon/src/swarm/benefit.rs`, `daemon/src/swarm/admission.rs`, `daemon/src/swarm/artifacts.rs`, `daemon/tests/swarm_admission.rs`, `daemon/tests/swarm_runtime.rs`.

Remaining: only the fixture path commits these decisions. Planned exact-name resource conflicts now constrain independence, but the estimator still trusts caller-supplied costs, undeclared-resource independence and allocation figures; fresh shared-account headroom is not yet an input. No live director produces estimates. The measured value spans supervised run creation through exit, so it can include setup or queuing; actual native-unit usage and planning/context/integration/review actuals are still unavailable. Earlier waves remain durable in SQLite but do not yet have a paged history API. The no-decision path permits one worker alongside the director, rather than a fully qualified single-agent fallback. Auto Mode and the shared reservation authority must supply live data before normal scheduling uses this gate. The RFC criterion stays unchecked.
