# SWARM-05 — serial versus parallel benefit

Status: partial. Revisions: `1aa56f9` (measured outcomes), `0d2074c` (planned resource independence), `b72f962` (active-wave refill). Support level: fixture-only, committed benefit decisions, admission gate and measured worker wall time.

Input: two paired plans estimate the same two independent jobs. Each plan supplies planning, context transfer, worker execution, retry allowance, integration and review costs in elapsed milliseconds and native quota units. The fixture compares a 240 ms serial plan with a 210 ms parallel plan, 40 milli-points of allocation and 10 milli-points reserved to finish. Variants increase parallel context cost to remove the time benefit, reduce finishing reserve, exceed total allocation, make the jobs dependent, or make both plans unaffordable. Another fixture removes a phase estimate, changes a job identity, or supplies an uncalibrated worker estimate. Admission fixtures exercise no decision, committed serial and parallel decisions, daemon restart, changed decisions while workers are active, job IDs outside the batch, and a second batch after two workers submit accepted evidence and exit. A supervised `/bin/sleep 1` worker supplies a measured terminal run timestamp, followed by another daemon restart. Existing 32-worker, review-pressure, scheduler, dispatch, context and outage fixtures now declare synthetic beneficial batches when they expect concurrent admission.

Expected: choose parallel only for independent jobs with a strict time benefit, affordable total usage and enough finishing capacity. Prefer serial on ties. Reject incomplete or inconsistent estimates. An unproven run must not fan out; a committed decision must survive restart and bound the specific batch without bypassing quota, worker or global ceilings.

Observed: `swarm.benefit.preview` selects the two-worker parallel plan with a recorded 30 ms expected gain, 35 milli-points total usage and 10 milli-points finishing cost. It returns serial when coordination erases the benefit, reserve or allocation is insufficient, or jobs are dependent; it reports blocked when neither path is affordable. Malformed estimates fail. A fixture-only `swarm.benefit.commit` persists the effective estimate and decision by plan revision and wave. With no decision, the second active worker is blocked. A serial decision holds it too; a parallel decision admits only estimated jobs, subject to the existing quota and concurrency checks. The decision and replay survive daemon restart. A changed estimate for admitted jobs is rejected. A new ready-job batch can now commit while prior workers remain active: after one of four workers exits, a new wave refills the fourth slot while a fifth concurrent admission stays blocked. The S1 Atlas joined replay exercises this with J5 after J1 exits and J2/J3/J4 continue. Each admitted attempt retains its estimated elapsed time and native-unit usage. After a supervised exit, the daemon records measured run wall time atomically with exit confirmation; `swarm.get` exposes that measurement after restart. Native-unit actual usage remains null because no authoritative provider receipt exists. A fixture with overlapping planned write claims forces a serial choice with `resource_conflict`; read-only overlap remains available to the admission claim rules. The full offline Rust suite passed at `b72f962`; the opt-in Atlas replay passed separately.

Commands: `cargo test --offline -p overseerd --test swarm_benefit -- --nocapture`; `cargo test --workspace --offline -q`.

Evidence: `daemon/tests/swarm_benefit.rs`, `daemon/src/swarm/benefit.rs`, `daemon/src/swarm/admission.rs`, `daemon/src/swarm/artifacts.rs`, `daemon/tests/swarm_admission.rs`, `daemon/tests/swarm_runtime.rs`.

Remaining: only the fixture path commits these decisions. Planned exact-name resource conflicts constrain independence, but the estimator still trusts caller-supplied costs, undeclared-resource independence and allocation figures; fresh shared-account headroom is not yet an input. No live director produces estimates. The measured value spans supervised run creation through exit, so it can include setup or queuing; actual native-unit usage and planning/context/integration/review actuals are still unavailable. Earlier waves remain durable in SQLite but do not yet have a paged history API. A later decision lists only its newly estimated jobs, so a pending job from an earlier wave must be carried into the new decision before admission. The no-decision path permits one worker alongside the director, rather than a fully qualified single-agent fallback. Auto Mode and the shared reservation authority must supply live data before normal scheduling uses this gate. The RFC criterion stays unchecked.

App-cap follow-up at `17be43e`: with `agents.max_active=2`, a two-job benefit estimate now commits a serial decision, `global_agent_limit` reason and a one-worker ceiling. With `agents.max_active=3`, a three-job batch can still be estimated while its committed simultaneous worker ceiling is two; admission holds the third until a slot frees. Both focused tests failed before the fix and passed afterward. `cargo test --workspace --offline -q -- --test-threads=1` passed 199 tests with 11 ignored. The elapsed-time comparison still assumes the submitted parallel jobs overlap fully, so its expected gain can be optimistic when they must run in waves; current occupancy from other tasks is enforced at admission rather than fully represented in the benefit estimate.

Capacity-estimate follow-up: the committed estimate now uses at most `min(agents.max_active - 1, policy.max_workers)` simultaneous worker slots. A three-job, two-slot fixture takes two 100 ms worker waves: parallel elapsed time is 310 ms including overhead, versus 340 ms serial. Raising parallel context overhead makes it 350 ms and correctly chooses serial. The new test failed at 210 ms before the correction. The focused nine-test benefit suite and full serialized workspace suite passed (200 passed, 11 ignored). Current occupancy from other tasks is still enforced at admission rather than predicted in the benefit estimate; actual model usage, real phase timings and the shared Auto Mode quota input remain absent, so SWARM-05 stays partial.
