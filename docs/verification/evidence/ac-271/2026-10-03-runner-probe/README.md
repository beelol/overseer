# Synthetic macOS runner probe

2026-10-03, macOS 26.6.2 (25G83), arm64. Design investigation alongside main `a864957c`; no production implementation or transformer installed. Only synthetic data under `/private/tmp/overseer-transformer-isolation-probe-20261003` was used. No owner paths, profiles, credentials, external connections or paid turns were accessed.

The earlier deny-default profile aborted before even `/usr/bin/true` ran. Differential controls isolate a required literal-root file-read allowance: adding broad file reads lets the inert command exit0, adding Mach lookups does not, and permitting the literal `/` fixes startup while `/private`, `/dev`, `/usr` or `/Library` alone do not. The literal root allowance is not recursive. Python additionally needs ancestor metadata and entropy-device reads. The `/usr/bin/python3` selector shim failed before execution; the explicit Xcode Python executable avoids that shim. All startup failures remain in the receipts and are not counted as enforcement results.

`runner-v6.sb` retains deny-default, narrow temporary scratch writes, read-only synthetic program content, system runtime reads, same-sandbox signaling and process fork/exec. Direct execution exited0: scratch write allowed; synthetic protected content read/write, program write, symlink escape, task-owned loopback connect and fake Unix daemon connect all returned EPERM. Neither listener accepted a connection. An unsandboxed control allowed all seven operations and both listeners accepted connections, proving real targets existed.

`nice -n 20 python3 run-probe.py` also exited0 with all assertions passing. It runs a sandboxed Python parent that spawns the probe child, then an unsandboxed positive control. The child inherited the same six denials; scratch remained writable. Both parent and child exited, sockets were closed and unlinked, and positive-control injected files were removed. Socket creation alone was allowed, as expected; actual connection attempts establish the tested denial.

Saved sources and SHA256 receipts retain the exact experiment. These are evidence scripts, not an installed runner or portable tests. Paths in the profile refer to the original temporary tree. To repeat elsewhere, copy the layout, replace that one root path throughout the profile, create allowed/forbidden directories with a synthetic-credential file, and link allowed/escape to that synthetic file. The Python executable/system runtime policy must be qualified for that machine rather than silently widened.

Limits: no RTK execution, installation rollback, pin replacement/confirmation, output/time limits, forced descendant termination, daemon lifecycle integration, other-platform qualification or native result-hook capture. Fork inheritance is not proof of descendant cleanup on timeout. AC271–273 remain unverified. Use these results to design the bounded runner; do not ship any permissive diagnostic control profile.

## Child-process denial follow-up

Alongside main `9dfa4359`, a separate `runner-no-fork.sb` removes only the process-fork allowance from v6. `nice -n 20 python3 run-fork-probe.py` exited0: both direct `os.fork()` and subprocess execution failed with EPERM inside the sandbox, while the unsandboxed positive controls each spawned and reaped a successful child. Parent processes exited and all successful control children were reaped. The saved driver was executed after creation; `fork-sha256.json` pins its inputs and results.

This supports evaluating a no-child-process runner for a transformer that does not need subprocesses. It is not yet the selected production policy: RTK compatibility, native threads, exec replacement, timeout/output bounds and forced cleanup remain unqualified. No external executable was installed or run; AC271–273 remain unverified.
