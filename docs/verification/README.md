# Verification ledger

The authoritative criteria text and checkboxes are in [the RFC](../overseer-rfc.md); the
[root README](../../README.md#acceptance-criteria) mirrors the checkbox list with evidence
links. Both are generated from the evidence records (`AC-NN.md`) in this folder. Records
AC-01 and AC-03 are hand-written; the others are generated by [`records.py`](records.py)
from structured entries so wording stays consistent (`python3 docs/verification/records.py <commit>`).

Statuses: `not started`, `in progress`, `implemented / unverified`, `blocked`, `verified`.
Only `verified` gets `[x]` (in the RFC and the README).

## Status by criterion

See the [acceptance criteria list in the README](../../README.md#acceptance-criteria) for every criterion's checkbox, status and evidence link.

## Evidence layout

- `evidence/ac-01/` — harness help/probe logs (AC-01).
- `evidence/ui/<scenario>/` — packaged-VS Code runs: `install.log` (VSIX install via `code`),
  numbered screenshots captured from the real workbench, `scenario.log`, `result.json` with
  every check. Scenarios live in [`test/ui`](../../test/ui):
  - `main` — OpenCode (mock model) task from the command palette, Follow/pause/resume/off,
    review edit, follow-up, interrupt, native grandchild controls, daemon crash + reconnect.
  - `codex-live` — **live** Codex (owner's ChatGPT login, 4 tiny turns): dogfood edit on the
    Overseer repo, native sub-agent, review edit, follow-up, VS Code closure, interrupt.
  - `review` — two repos, agent switching, attribution, refresh timings, unsafe/unsupported
    files, current-checkout editing, native undo/redo, drafts across reload.
  - `codex-approval-live` — **live** Codex app-server transport: Allow, Deny and Interrupt
    on real permission requests (3 tiny turns).
  - `codex-follow-live` — **live** Codex app-server turn alternating edits across files at
    distant lines: Follow, pause during live edits, Resume.
  - `trust` — Restricted Mode blocks launching.
  - `perf` — 10,000 files, four active runs, 10 minutes.
- `fixtures/transcripts/` — recorded live transcripts (paths redacted) and mock-provider runs.
- `evidence/ac-04/`, `evidence/ac-37/`, `evidence/ac-40/` — clean-clone build, test run and
  fresh-reader logs.

Coverage labels used in every record: **live** (real harness, real account), **mock**
(real harness process, deterministic mock model provider), **fixture** (recorded/synthetic
transcripts or fixture executables through the real adapter/daemon). Fixtures never satisfy
live-only criteria.

## Record template

```markdown
# AC-NN — criterion title
Status: in progress | implemented / unverified | blocked | verified
Tested implementation commit:
Verification date and verifier:
OS / architecture / VS Code / harness versions:
Harness, provider and redacted account identities (if applicable):
Prerequisites and fixture:
Steps or exact reproducible commands:
Expected result:
Actual result:
Evidence paths (test logs, redacted transcripts, screenshots/recording):
Live vs fixture coverage:
Known limitations and remaining platform/account combinations:
Blocker, attempted alternatives and next action (if blocked):
```

Use repository-relative artifact links. Keep logs concise and redact secrets, personal
account information, and unrelated private source before committing. Do not store auth
homes, browser cookies, tokens or raw credential stores. Evidence identifies accounts only
by one-way fingerprints (`profile.status` → `identity.account_fingerprint`).

An implementation commit is the revision tested, not necessarily the later documentation
commit recording the result. Re-run affected checks when behavior changes, and reopen
criteria on regressions. Keep README's verified count synchronized in the same update.
