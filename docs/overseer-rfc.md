## Product and boundary

Overseer is a local Rust orchestration daemon with a VS Code control surface and an
integrated Branch Diff review experience. It launches account-authenticated agent
harnesses, tracks their runs and descendants, and lets the user follow and edit their
work. The daemon owns durable state. Closing VS Code must not end the work.

A harness is the agent runtime (for example Codex, Claude Code, or OpenCode), not the
model or account. OpenCode is one harness, not the umbrella for all harnesses. A remote
agent service such as Devin may require a different adapter and workspace model.

The first usable release includes multiple accounts, native child visibility testing,
and editable worktree diffs. These are not postponed until after the first release.
The initial implementation can use smaller milestones, but cannot call an intermediate
milestone the completed product. A usable macOS milestone may retain explicitly unchecked
Linux and unavailable native-telemetry criteria; it must disclose those gaps.

## Proposed defaults, distinguished from confirmed decisions

These resolve implementation details without presenting them as prior user decisions.
Changing them requires a recorded RFC revision, not a hidden implementation shortcut.

- Native delegation observation comes first. Overseer-created child scheduling, Auto
  routing, races, and quota-based escalation are later work.
- Use SQLite for state/events and a versioned local protocol. Prefer a Unix socket with
  owner-only access. A localhost HTTP transport would also need authentication.
- Prefer structured harness protocols/events; use a persistent process/session backend
  where necessary. Evaluate tmux for interactive fallback. Do not force a structured
  harness into terminal scraping merely to standardize on tmux.
- Confirmed Follow behavior has `off`, `following`, and `paused by navigation` states. Manual selection of
  another file or deliberate scrolling away pauses it; an explicit Resume action starts
  it again. It does not resume on a timer and interrupt reading. Turning the checkbox
  off preserves file, selection, and scroll as far as the changing text permits.
- Review and Follow use the same live data. Review disables automatic navigation.
  Switching to another agent does not inherit Follow accidentally.
- Review comments sent to agents, automatic merges, and automatic worktree deletion are
  later work. Editing and native editor undo are required now. Hunk accept/reject was
  moved into scope by the owner on 2026-09-25 (AC-42).
- Stable VS Code on macOS is the current verification target. Keep platform-dependent
  paths, processes and credential stores behind portable boundaries for Linux; Linux
  verification is deferred under AC-41. VSCodium, Windows and Remote SSH are later qualifications.
- No embedded inference model in v1. First exhaust structured events, session records,
  hooks and deterministic parsing. A speculative 512 MB model is not a dependency.

### Exact comparison semantics

For a selected run, let `H` be current HEAD, `T` a selected comparison branch,
`M = merge-base(T, H)`, `S` the immutable task-start snapshot, `R` the latest run-start
snapshot, `F` the recorded original fork commit, `I` the index and `W` the working tree.
Snapshots record relevant file contents and index state, including existing dirty and
nonignored untracked files, without committing, staging or stashing the user's checkout.
Capture the task-start snapshot once and a fresh run-start snapshot before each launch.

The confirmed default is **R → W**, labeled **Latest run**, so a new launch initially
shows no new run changes and then reveals that run's edits. Proposed boundary: each
user-submitted follow-up that starts a new work turn also gets a fresh snapshot; transport
reconnects and process recovery do not. Keep prior run baselines addressable. This defines
“since last run” as changes from the start of the latest run, not the end of its predecessor.
Unsaved buffers remain separate labeled drafts and are preserved before any launch.

The comparison picker also offers:

- **Since task start (S → W)**, preserving dirty starting contents rather than just a SHA.
- **Original fork (F → W)**, with its recorded commit and provenance. If unknown, show
  unavailable or clearly label a detected candidate; do not invent historical certainty.
- **Target/other branch**, allowing branch selection and explicitly labeled merge-base
  (**M → W**, PR-style) or direct branch-tip comparison.

The base icon exposes selected mode, snapshot/run identity or actual refs/SHAs, and detected
parent information. Target selection defaults to the configured integration branch, then
repository default; unresolved branches/bases show an explanation. A rebase cannot silently
rewrite a recorded run/task snapshot or historical fork.

The selected comparison's changes form the main file list. A separate always-visible
**Workspace dirty** section exposes all staged (`H → I`), unstaged (`I → W`) and nonignored
untracked files, including pre-existing changes; deduplicate file rows or label sections
clearly. Thus an empty latest-run diff cannot conceal dirty work. Separate staged/unstaged
inspection remains available when net changes cancel out. Clean main/main is empty; dirty
main/main shows dirty work, not every unchanged file. Branch mode includes branch commits.

Unsaved editor buffers are additional visible drafts, labeled unsaved. Saving targets the
selected worktree. External writes must not silently overwrite a user's draft. Git dirtiness
alone proves a file changed, not who changed it: pre-existing/user edits remain visible and
must not be falsely attributed to AI.

## Architecture and ownership

The extension owns presentation, user navigation, and editor buffers. The daemon owns
repositories, tasks, execution targets, runs, process lifecycles, worktree identities,
persisted events and capability state. An extension reload rebuilds its view from the daemon.

Core records:

- `Task`: user intent, repository, target ref, task-start snapshot, recorded fork commit/provenance, acceptance metadata.
- `AgentRun`: task, parent run (optional), harness/version, account profile, provider/model,
  workspace, run-start snapshot, native session ID, lifecycle, timestamps and supported metrics.
- `Workspace`: canonical path, repository identity, worktree/current-checkout kind,
  branch, write ownership and initial dirty inventory. Children may share a workspace.
- `ExecutionTarget`: harness, isolated account profile, supported models/capabilities;
  credentials themselves do not belong in SQLite event payloads.
- `Event`: stable ID, run/session identity, ordering cursor, type, timestamp, source,
  evidence confidence and a bounded, redacted payload.

Adapter capabilities include launch, prompt, interrupt, resume, approvals, output,
file activity, children, usage and quota. Unsupported or unknown is different from zero.
Use exact structured IDs when available. Inferred child edges must carry provenance and
confidence; text saying “I delegated” is not sufficient evidence of a real child run.

Prefer one writer per workspace. Native children may intentionally share their parent's
workspace; record that relationship. Independent tasks default to separate worktrees.
Reject unexpected second writers to an existing checkout. Do not copy login state merely
by copying HOME: test each harness's credential-store and refresh behavior.

## Acceptance criteria

Only the checkboxes below are authoritative. A box is checked only when its evidence record is `verified`.
Each **Verify** clause is required evidence, not a suggestion. Fixture tests complement
real integration tests; they cannot substitute for subscription, native-child, or UI tests.
The owner explicitly permits mock/local-model verification for OpenCode AC-14 only;
record that coverage honestly rather than claiming paid-account or native-child verification.
Evidence and blockers live in [the verification ledger](verification/README.md).

### Gate E — workspace correctness

- [x] **AC-21 — Worktrees by default.** Each independent writing task gets an identified branch/worktree without mutating the source checkout. **Verify:** simultaneous tasks change identically named files independently; source checkout stays unchanged; existing branch/path collisions are handled without deletion.
- [x] **AC-22 — Current dirty checkout.** Explicitly choosing the current checkout records pre-existing staged, unstaged, untracked and unsaved work and leaves it intact. **Verify:** launch/edit/interrupt there, confirm original work remains, and distinguish initial dirtiness from observed run changes without inventing authorship.
- [x] **AC-23 — Shared workspace ownership.** Native children can share their parent's workspace; independent writers cannot accidentally claim it. **Verify:** shared parent/child edits remain visible under the right runs, a conflicting unrelated writer is rejected, and read-only labels are used only when access is actually enforced.
- [x] **AC-24 — Safe workspace retention.** Finished, failed and interrupted runs retain their work for review. Explicit cleanup reports dirty files and live users before removal and never removes the current checkout. **Verify:** untracked work, active child, interrupted task and current-checkout cleanup attempts preserve data.

### Gate H — review actions and run readability (added by the owner, 2026-09-25)

- [x] **AC-42 — Hunk accept and reject.** In the live review, each change against the selected comparison can be accepted (kept and marked reviewed) or rejected (restored to the comparison base in the selected run's workspace) one hunk at a time, with native undo. ### Gate J — daily-driver orchestrator UI (added by the owner, 2026-09-26)

### Gate L — Continuity: offline mode and local models (added by the owner, 2026-09-26)

Owner request (2026-09-26): the work must always get done. A lost connection changes how, never whether. The mode is called **Continuity** and is on by default, explained once on first use. Offline is determined from the system itself (is the machine connected?), confirmed by probes and by every agent failing on connection errors; it is different from one provider being down. If one provider is down and another works, use the best working one (OpenAI, then Anthropic, then other providers with accounts). If nothing online works, move the work to the best local Ollama model this machine's real memory allows, starting with the Qwen coders, downloading the model (and Ollama itself) only when the settings allow. With Continuity off, say that Overseer is offline and keep retrying for up to 36 hours, offering local models for new agents meanwhile. Memory is read from the machine, cross-platform where practical and straight from the kernel on macOS: 40% of total by default, never above 50%, and never more than what is free now minus headroom, reassessed for every new run and turn. Built in its own worktree and pull request at the owner's request. Design: [Continuity RFC](rfcs/offline-mode.md).

- [ ] **AC-83 — Offline is not an outage.** The daemon keeps one connection state, online, degraded (named providers unreachable) or offline (no working connection), decided from three sources in order of trust: the system's own connectivity answer (macOS SystemConfiguration reachability and default route; Linux NetworkManager connectivity or the default route), credential-free probes (a certificate-verified baseline by name and by IP, and one per provider), and a new `network` error class from the agents (every active provider failing on connection errors is offline-level evidence); changes are debounced, auth, rate-limit and quota errors never change the state, and every change is an event with the reason, the system's answer and per-provider health. **Verify:** on this machine, turning Wi-Fi off gives offline within 10 s from the system signal and turning it on gives online after the checks agree; protocol tests with fixture system answers, probe results and harness errors: connected system with a failing baseline gives offline (DNS or portal), one provider failing gives degraded naming it, all providers failing with probes off gives offline, a 429 and a usage-limit error leave the state online; the status bar and side bar show each state.
- [ ] **AC-84 — Fail over to the best working provider.** With Continuity on, a run whose provider is unreachable continues on the best other online provider in the order OpenAI, Anthropic, then other providers with accounts (`continuity.providerOrder`), that has an installed harness and a signed-in account, through a handoff in the same task and workspace, announced in both chats; local is used only when no online provider works; with Continuity off the run waits (AC-92). **Verify:** fixture harnesses for two providers, one failing with network errors while the other works: the successor starts on the other harness within 30 s, the predecessor reads handed off (not failed), the review keeps the same worktree, the announcement names the reason; the order is honoured when both alternatives work; with every provider failing no failover happens and the offline policy applies; a live check with Codex's hosts blocked and Claude working, tiny prompt.
- [ ] **AC-85 — Local inventory read from the machine.** `local.inventory` reports total and available memory and memory pressure read from the operating system through one platform module (macOS: `hw.memsize`, `host_statistics64` free + inactive + purgeable pages, `kern.memorystatus_level`; Linux: `/proc/meminfo` and `/proc/pressure/memory`), Ollama presence, version and running state, installed models with size, family, quantization, context length and capabilities, model geometry, loaded models with measured memory, and free disk; unknown is reported as unknown; nothing is tuned to one machine. **Verify:** on this machine the memory numbers match `sysctl`, `vm_stat` and `memory_pressure` within 5% at the same moment and the model report matches `/api/tags`, `/api/show` and `/api/ps`; a unit test feeds Linux `/proc` fixtures through the same module; with Ollama stopped, and with it hidden from PATH and `/Applications`, the report says so without guessing; a protocol test with a fixture Ollama server.

### Gate N — phone remote on the same network (added by the owner, 2026-09-26)

Owner request (2026-09-26): control Overseer from the phone. See the output of any agent, talk to any agent and to Overseer itself, and reach every Overseer system, with full control and without losing the session: *if it's on, you can access any agent through your computer from your phone*. The phone talks only to Overseer on the Mac, never to a harness. The first step is the same network, through a gateway inside the daemon that is off by default; a relay for use away from home is wanted later as its own RFC and gate and is not part of this one. The app is for iOS (the owner's iPhone; the owner has an Apple Developer membership) and Android (emulator only for now). This gate is a recorded revision of the local-only default: the Unix socket boundary (AC-08) stays as it is, and the gateway is a second, authenticated entrance. Design, the owner's decisions, the proposed defaults and the open questions: [phone remote RFC](rfcs/phone-remote.md). Prepared goal: [phone-remote-goal.md](rfcs/phone-remote-goal.md). Built in its own worktree and pull request.

- [ ] **AC-115 — Feasibility and reuse before lock-in.** Before the design is fixed, spikes prove: one app build (Expo proposed) running on the iOS simulator and the Android emulator that holds an encrypted session to a gateway prototype and resumes it after the app was in the background; the chosen handshake and cipher working between the Rust daemon and the phone runtime on both platforms; Bonjour discovery and the local network permission on a real iPhone; a push notification sent from the Mac to that iPhone with the owner's key. Happy (MIT) is inspected at a recorded revision and the decision on what to adopt (chat list, diff rendering) is written down, with license and notices kept for anything adopted. **Verify:** spike logs with versions; shared test vectors passing on both sides; the iPhone's discovery and push shown in a screenshot or recording; the reuse decision in `docs/source-assessment.md`; a blocker found here changes the RFC before any criterion below is built.
- [ ] **AC-116 — A gateway that is off by default.** `overseerd` gains a gateway listener for phones, separate from the Unix socket. It does not listen until the owner turns phone access on; turning it off closes the listener and every session within 1 s; the daemon persists and enforces the setting with VS Code closed; nothing answers before a session is authenticated; connections from outside private and link-local address ranges are refused; failed handshakes are rate-limited and logged. **Verify:** protocol tests: the port refuses connections by default, listens after enabling and drops sessions on disabling; unauthenticated, malformed, oversized and truncated input gets no protocol reply and no crash; a public source address is refused; the AC-08 tests pass unchanged with phone access on and off.
- [ ] **AC-117 — Pairing needs the Mac.** Pairing starts only on the Mac (*Pair a Phone* in VS Code, or `overseerd ctl`), which shows a QR code and the same content as a typed code: the gateway's key fingerprint, the addresses to try, and a secret valid once and for two minutes. The phone scans or types it; the Mac shows the device's name and asks the owner to confirm; only then is the device stored with its own key. A wrong, expired or reused secret pairs nothing, a declined confirmation pairs nothing, and five failures close pairing until it is started again. **Verify:** protocol tests for each refusal and the lockout; a packaged-UI screenshot of the code and the confirmation; the simulator and the emulator pair by typing; the owner's iPhone pairs by scanning.
- [ ] **AC-118 — Encrypted and mutually authenticated.** Every session is authenticated in both directions with the keys from pairing and encrypted at the message layer with an established construction chosen in AC-115 (Noise IK proposed): forward secrecy per session; a tampered, replayed or reordered frame ends the session; nothing of the protocol is readable on the wire; the session layer does not depend on the transport, so a later relay can carry it unchanged. **Verify:** a packet capture of a live session contains no method name, prompt or output text; protocol tests refuse an unknown device key, a gateway with the wrong key, a tampered frame, a replayed frame and a replayed handshake; the same test vectors pass in the daemon and in the app.
- [ ] **AC-119 — Devices, scopes and revoking.** The Mac lists paired devices with name, platform, scope, paired time, last seen and address. A device is *Full control* (the default) or *Watch only*. Every daemon method is classified as read, control or Mac only, and an unclassified method fails the test suite; pairing, managing devices and stopping the daemon are Mac only. Revoking ends the device's session within 1 s and its key never authenticates again. Every command from a phone is recorded as an event with the device as its source. **Verify:** a table-driven protocol test over the daemon's full method list: a Watch only device is refused on every control method and every device on every Mac only method; a method added without a class fails the build; revoke during a live stream; events show the device; a screenshot of the Devices list.
- [ ] **AC-120 — Found on the network.** While phone access is on, the daemon advertises the gateway over Bonjour and stops when it is off. The phone finds its Mac by key, so a changed address needs no new pairing, and a machine with the same name and another key is refused with a clear message. A manual address always works. iOS's local network permission is explained before the system asks, and a denied permission says what to do. **Verify:** the owner's iPhone reconnects without pairing again after the Mac's address changes; an impostor fixture advertising the same name with another key is refused; the emulator connects through a manual address; screenshots of the permission explanation and the denied state.
- [ ] **AC-121 — Never lose the session.** After the app was in the background, the phone was locked, Wi-Fi dropped, the daemon restarted or the Mac's address changed, opening the app shows every event exactly once and in order, with no manual reconnect, no missing message and no duplicate. Truncated history reloads state and says so. The app opens on cached state marked with its age and never shows stale state as live. **Verify:** a protocol test through the gateway cuts the connection at 100 random points during a fixture stream and compares the phone client's sequence with the daemon's log: identical; simulator and emulator scenarios put the app in the background for five minutes during a stream of numbered lines, then restart the daemon mid-stream: the lines are contiguous; screenshots of the cached and reconnecting states.
- [ ] **AC-122 — Sent exactly once.** Every changing request from a phone carries a request id. The daemon stores the outcome per device and id for at least 24 hours and answers a retry with the stored outcome instead of acting again. A message typed without a connection is kept on the phone, shown as queued, and sent once when the session is back. This covers starting an agent, follow-ups, permission answers, stop, hunk actions, merge back, pull request and cleanup. **Verify:** protocol tests: the same id sent three times at once produces one turn and three identical replies; a connection cut after the request was written and before the reply, then a retry, leaves one turn in the store; a phone scenario sends with the network off and the agent's chat shows one message after reconnecting.
- [ ] **AC-123 — The Mac stays awake while it matters.** While phone access is on and a run is active or waiting for the owner, the daemon holds a power assertion that prevents idle sleep; it releases it when no run needs it; both are events. When the Mac cannot be reached the phone says *Mac unreachable* with the last contact time. The README states the limit: a closed lid on battery sleeps anyway. **Verify:** `pmset -g assertions` names Overseer's assertion during a fixture run and not after it; with phone access off no assertion is taken; a phone scenario with the gateway stopped shows the unreachable state and the time; the README text.
- [ ] **AC-124 — See every agent.** The phone lists every agent the side bar lists, with the same hierarchy (children and grandchildren), status and provider logo, agents that need the owner first, with filter and search. Opening an agent shows its conversation live, to the same content as VS Code's chat: text, folded tool steps, edits, permission requests, errors, and turn results with tokens and cost. A streamed line reaches the phone within 500 ms at p95 on the local network. **Verify:** a scenario with nine fixture agents and a nested child: the phone's list equals the daemon's `state`; each conversation is compared item by item with VS Code's chat model for the same run; the delay is measured from the printed timestamp to the rendered line, as in AC-58; screenshots on iOS and Android in light and dark.

## Verification and completion rules

Statuses: `not started`, `in progress`, `implemented / unverified`, `blocked`, `verified`.
Only `verified` gets `[x]`. Count milestone progress separately from product completion.
Never delete, soften, defer or rename a failing AC solely to declare success. Scope changes
need a recorded owner decision; keep the original ID and explain any replacement.

The owner authorizes the implementer to record reproducible evidence and mark criteria
verified; a separate review pass can follow. No separate reviewer is required now.
Claims of complete feedback require known coverage, with gaps explicitly disclosed.

AC-01–03 are research gates. AC-04–40 and AC-42–66 describe the macOS implementation and
evidence scope; AC-41 retains Linux qualification as deferred and unchecked. A usable macOS milestone may
be delivered with documented unavailable native telemetry (AC-19) and inaccessible account
verification left unchecked. Codex/Claude account integration and OpenCode integration remain
